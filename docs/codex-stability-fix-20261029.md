# Codex 稳定性限定修复与验收（2026-10-29）

本轮保留 HEAD 9991ccb 上已有 v300–v303 本地修改，按用户授权只处理 Codex 强度确认、发送确认、显式首屏及连接／读取生命周期。源码实施前快照为 `_shots/codex-stability-fix-20261029/source-before`，不以整个工作区的 Git 差异冒充本轮修改。没有提交或推送 master/debug，没有测试、修改 Fusion。

## 实际修复

| 功能 | 根因 | 修改及边界 |
| --- | --- | --- |
| 思考强度 | 原生有 picker 与 power 两种现有控件来源，写入和回读选择了不同来源，造成生效后误报 | 选项、已选值和确认使用同一来源；未取得确认时明确报告尚未确认，不宣称已经失败，也不重复写入。Max 沿现有原生支持判断，不伪造能力 |
| Codex 发送确认 | 接受回执夹在正文、目录和状态的整包读取后；观察登记可能落在提交之后 | 提交前登记电脑端观察，轻量回执与正文读取分开；普通发送接受真实新轮次／原生开始时间或已接受消息，Queue 以原生队列记录确认，Steer 以原生接受的追加消息确认；手机计时不参与判断。观察范围按提交前最后一条原生轮次身份起算，不依赖该轮是否有计时信息；默认查询仍只读尾部两轮。未知结果不自动重发，原始读取错误可见，迟到成功结束同一请求 |
| 显式首屏 | 后台连接的 visible:false 阻止 attach 内的首屏，而 visible:true 又排在 attach 后执行 | 可见性只限制常规后台轮询，显式首屏允许完成；确认原生会话身份变化时取消旧读取，同身份复用已有来源。保留入口隔离、失败回初始页及正常后台节奏 |
| Codex 连接 | 普通绑定等待未使用的 Page.enable；协议 detach 未结束连接；旧 RA 监听跨中继重启残留 | 去掉无用途的 Page.enable 前置；Inspector.detached、断开和未打开连接返回真实原因；Codex 共享来源替换自身旧监听，去掉重复的监听刷新调度；原生 manager 识别结果按其存活作用域复用，不另起多套连接或刷新原生页面 |

本机原生页面实查曾有 38 份 RA watcher、1114 个 RA binding 名称。其中 4 份为更早的 timer／observer 结构，没有当前 stop 接口；用户另行授权后，一次性断开这些 RA 旧对象并清除定时器。产品不增加旧版兼容分支。其余当前结构监听由本轮生命周期释放；实际验收时原窗口和隔离窗口均只保留 1 份。监听积累是确定事实，但没有把所有原始超时都归因于它。

## 已完成检查

12 项内部合约检查通过：power／picker 强度来源；正文未返回时原生新轮次仍能确认；旧轮次不能认领新发送；Queue／Steer 不以运行计时确认；原始读取错误保持未知及迟到接受；同一消息的轮次／正文证据去重；不可见状态显式首屏；会话变更取消旧读；登记先于提交；协议 detach 结束在途调用。证据：`contracts.json`，这是受控检查，不冒充实际手机或第二台电脑。

配对 Chrome 已完成 13 项检查，详细结果在 `browser.json`：

- 实际发布资源、v304 缓存和普通刷新，复用原配对。
- 原 Codex 会话在中继重启后可读取；隔离项目打开并读取首屏。
- 强度经手机修改、原生选中及成功回执一致，再恢复原选值。
- 普通发送确认约 1731ms；Queue 约 921ms；独立运行中的 Steer 约 1475ms。另一次普通发送约 909ms。这些是隔离任务样本，不是对全部网络／模型状态的时延承诺。
- 在不可见状态显式 attach，随后恢复可见，首屏可结束；生成中刷新 RA 恢复同一会话，不刷新 Codex。
- 使用真实可用窗口，Cursor、Devin、Codex 进入／返回分别约 704ms、1055ms、704ms；只检查受影响连接，没有重测其业务适配。
- 导航／刷新后监听仍为 1；受控手机 UI 保留原始未知错误，真实接受结果到达后替换为已发送，不清除另一个草稿。

测试脚本曾在 RA 刷新初始化期间直接访问尚未声明的 APP_VERSION，属于脚本等待缺口，修正测试等待后继续，没有因此修改产品。强度测试也等待原生已有能力就绪，不以尚不可操作时的点击当作强度失败。

## 验收发现的额外事项及授权

1. Cursor 旧恢复记录返回“这条 Agent 已经不在列表里”。用户明确要求只记录，本轮不修；上述连接检查显式选择当前真实窗口，没有把旧记录恢复记为通过。
2. 普通发送后快速连续排队、立即追加的组合未取得追加回执，文字留在原生草稿。独立运行中的追加已通过，未将组合失败掩盖为成功。用户授权继续定位后，隔离复现确定：`submitCodexMessage` 向上扩大查找范围，误点排队行自己的 Steer，原生队列从 1 变为 0，而本次草稿仍保留。这是按钮归属错误，不是应该自动重发或延长回执等待。用户再次明确授权后，仅将按钮查询限定到原生 `[data-composer-body]` 输入容器，没有对应按钮时保留显式 steer 调用。补验连续发送→Queue→Steer通过：本次追加取得独立消息回执、原队列仍在、草稿清空；样本耗时分别为 1526ms、1604ms、4232ms。证据 `boundary-finding.json`、`boundary-verify.json`，失败现场私有状态也保留，没有删除失败证据。

另补 3 项按钮归属内部检查和 3 项回执范围内部检查，共计 18 项内部检查；浏览器结果为前述 13 项加连续操作补验。没有因改测试脚本重复执行已通过且未受影响的检查。最终 `npm run check` 通过（98 个语法文件、102 种前端发送协议、69 种后端回包、196 个 helper、65 个模块导入），`git diff --check` 通过。
