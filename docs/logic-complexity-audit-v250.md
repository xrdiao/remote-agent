**存在把简单行为交给过多状态和链路共同控制的情况。最值得处理的是发送确认、连接与会话就绪、异步请求调度、聊天内容补全、滚动与历史请求、会话元数据。**

共同问题不是某个文件太长，而是：

- 同一个事实有多个判断来源，例如“已发送”“已就绪”“会话名称”。
- 展示、读取、修改原生界面混在一条流程中，为避免冲突又增加锁、重读和回退。
- 一个操作的开始、完成、失败、取消分散在不同模块，容易只进入等待而不退出。
- 旧行为已经取消，相关状态和分支仍留在主流程中。

有两点必须区分：

1. **v250 已经拆开窗口发现与首屏读取，并修正 Codex 发送确认。** 本轮不能再把之前的加载死锁和 Codex 输入框判失败写成尚未修复。剩余问题是相同职责在其他路径仍不统一。
2. **当前滚动没有继续用旧阅读锚点反复拉回位置。** 仍可精简的是手势、渲染延迟、回底、历史插入之间的调度，以及未启用的旧分支。不能通过恢复阅读锚定、取消惯性保护或删除历史插入保位来“简化”。

建议逐类修改，先统一事实来源和结束条件，再删除确认无效的旧逻辑。不要同时重写所有模块，也不需要引入新的前端框架或大型通用状态管理系统。

## 4. 详细发现、简化方式与影响

### S01 · 三种 Agent 对“已发送”的定义不同

**证据：源码确定＋隔离复现。** [Cursor submitPrompt](../server/apps/cursor.mjs#L180)、[Devin submitPrompt](../server/apps/devin.mjs#L260)、[Codex submitPrompt](../server/apps/codex.mjs#L172)、[通用发送](../server/agent/chat.mjs#L597)、[手机回执](../app/js/composer.js#L35)。

- Codex 在 v250 已改为确认新增消息／队列，无法确认时返回待确认。
- Devin 仍先判断原生草稿是否变化；隔离条件下，新增消息或队列已存在、输入框暂未清空，40 次循环后仍报“未确认接收”。这是与刚修复的 Codex 问题相同类型的判定风险。
- Cursor 按下 Enter 后直接返回，适配器没有读取原生接受证据。这能确定“缺少确认”，不能据此说本轮真实 Cursor 已丢消息。
- 手机随后又通过聊天内容补认成功，相当于三个原生标准再叠加一个前端标准。

**简化：** 三个适配器统一返回 `accepted / queued / unconfirmed / rejected`，附原生消息或队列标识。通用层只处理这个结果，手机只让同一个请求状态向前推进。保留聊天内容的迟到核对，但让它更新同一请求，而不是产生第二种成功标准。

**影响与效果：** 影响三 Agent 发送、排队、立即追加、失败草稿及迟到回执；会减少误报和状态反转。会改变 Cursor 目前较乐观的确认时机，可能多一小段确认等待，不能承诺发送更快。必须保留附件、同文本重复发送的区分、新草稿保护和不自动重发；终端另有语义，不并入聊天接受标准。

### S02 · 加载就绪仍由多层状态共同描述

**证据：源码确定，剩余复杂度；不是复述已修复死锁。** [加载页](../app/js/gate.js#L182)、[导航开始](../app/js/net.js#L69)、[窗口初始化](../server/session.mjs#L182)、[首屏读取](../server/agent/chat.mjs#L166)。

当前相关事实分布在 `conn.loaded`、`windowReady`、`selectionReady`、`navigationPending.confirmed`、`bindingReady`、`startupPending`、`pendingProject`、`switchingThread` 等位置。其中一些确实含义不同，不能直接合成一个布尔值。复杂之处是这些含义和先后关系没有统一出口，绑定、恢复、项目切换又会互相调用。

**简化：** 明确三个独立职责：

1. 连接是否认证成功。
2. 本次选择是否已绑定并取得可用首屏，含选择 ID、请求 ID 和阶段。
3. 安装／窗口目录，仅负责展示和启动，不决定当前聊天是否就绪。

手机的发送可用性从本次选择状态派生；缓存预览仍只读。加载动画、首屏绘制、原生详情补全各自处理，不再反过来改变绑定的业务事实。保留 v250 的先进入、失败重试、首屏先返回、初始总超时和新选择取消旧读取。

**影响与效果：** 影响首次打开、恢复后台窗口、启动 Agent、跨项目切换、部分失败进入。减少“绿色窗口但聊天不可读”等状态解释分歧。风险是过早启用输入或错误复用旧首屏，因此必须验证信任提示、登录、新建空会话和缓存预览。

### S03 · 调度规则分散，等待次数不能代表总耗时

**证据：源码确定＋隔离复现。** [WebSocket 调度](../server/ws.mjs#L14)、[路由描述](../server/routes.mjs#L89)、[Session 调度](../server/session.mjs#L438)、[waitFor](../server/agent/context.mjs#L187)。

同一个命令是否只读、可后台执行、需要聚焦、属于连接命令、可被切换取消，分别由 `SWITCH_READS`、`CONNECTION_MESSAGES`、路由标记及 Session 判断。新增功能要同时记住多份分类。部分等待又采用“循环次数 × sleep”，每次 CDP 调用还自带超时；隔离检查中 10 次、每次读取 5 秒，实际预算变为 51.2 秒，并非 sleep 合计的 1.2 秒。v250 的初始 attach 有 30 秒总界限，但其他交互不能因此视为都有总界限。

**简化：** 在现有路由描述中集中声明读／写、归属、是否可取消、是否需要原生 UI 事务。一次用户操作携带一个总等待截止时间，内部调用使用剩余预算；不要再增加一层彼此独立的重试。保持写操作顺序，只合并可替代的读取。

**影响与效果：** 影响模型、目录、历史、会话管理等广泛功能，是高风险共享改动，应最后分阶段接入。收益是等待可解释、切换能及时生效。不能丢弃发送、文件保存、新建、删除等写操作；也不能把 UI 操作误标为无副作用读取。

### S04 · “读取聊天”还会展开、收起和补抓原生内容

**证据：源码确定，结构风险。** [聊天读取及详情补全](../server/agent/chat.mjs#L202)、[Devin 思考抓取](../server/apps/devin.mjs#L435)、[原生变动监听](../server/agent/updates.mjs#L5)。

正文读取除了提取内容，还会展开／收起思考、任务、指令，再次提取、合并多份正文缓存。为防止与模型菜单及输入冲突，又有详情锁、聚焦锁、Cursor UI 读锁、重读标记。事件监听和轮询本身有用途；主要复杂度在于一次数据读取夹带 UI 修改。

**简化：** 热路径只做原生状态读取、规范化和发布；优先从原生数据结构读详情。只有确实需要展开才能读到的内容，才进入独立、可取消的详情事务，按用户展开或有限补全触发。已有首屏不等详情的行为继续保留。

**影响与效果：** 影响思考全文、任务明细、执行记录、模型菜单与正文同步，可减少原生界面被后台读取干扰。代价是部分隐藏详情可能在用户展开后才加载。不能只删展开代码，否则原生 DOM 未挂载的详情会丢失；不能删除已有正文及历史缓存来掩盖缺失。

### S05 · 滚动需要保留核心能力，但可以减少重复调度

**证据：源码确定＋隔离检查。** [滚动状态](../app/js/history.js#L373)、[显式定位](../app/js/history.js#L438)、[补偿应用](../app/js/history.js#L474)、[渲染](../app/js/history.js#L623)、[历史插入](../app/js/history.js#L1370)。

- 触摸、惯性、滚动中、程序定位、滑块、延迟渲染、历史插入分别维护标记，并由滚动事件、ResizeObserver、动画帧和空闲计时器共同推进。
- `historyWaitingForIdle` 当前没有置为 `true` 的写入，`resumeHistoryAfterIdle` 仍被调用，属于停用残留。
- `scrollCorrection` 的新任务赋值当前只有 `kind: 'bottom'`，仍保留较通用的补偿调度外形。
- 显式定位函数同时清理 `historyPagePending` 等历史状态，手势定位与数据接收生命周期仍有交叉。

**简化：** 保留“跟随底部／自由阅读”两种内容展示模式；触摸、惯性、滑块归到同一交互状态。最新、发送回底、上下轮是一次性定位意图，由一个位置写入口执行。历史数据接收、缓存、待插入状态独立处理。先删除确定停用的分支，再统一调度，不一口气改写整个滚动器。

**影响与效果：** 影响所有聊天滑动和动态生成展示，减少状态组合与互相覆盖；不能保证只删几行就改善手感。必须保留：实际到底才吸附、手动离底立即退出、发送回底、点击最新中断惯性、上下轮只定位一次、历史插入仅一次保位、自由阅读时不持续调整位置。既不恢复旧阅读锚点，也不改成只依赖裸 `scrollTop` 的方案。

### S06 · 请求开始和结束没有统一约束

**证据：历史失败分支隔离复现；其他为结构风险。** [历史请求](../app/js/history.js#L1343)、[历史完成](../app/js/history.js#L1415)、[Question 提交](../app/js/history.js#L852)、[文件保存示例](../app/js/files.js#L367)。

历史请求先写入 `historyRequest`，再调用 `send`，没有处理发送返回 `false`。隔离检查中发送失败后，第二次加载被仍存在的请求拦住，直到后续选择／连接流程重置。Question、模型和批量操作也各自维护等待状态；文件保存已经有请求 ID、超时、断线结束等较明确的生命周期，不能把它也描述成同样缺陷。

**简化：** 给每类操作明确成功、失败、取消、发送未发出和超时出口，复用小型请求记录结构即可，不建设包办所有业务的“大请求管理器”。先修历史已确定路径，再让其他操作遵守相同约束。提示文字只展示状态，不作为业务完成依据。

**影响与效果：** 影响历史按钮、回答按钮、菜单等待、批量进度。等待能结束且可重试；超时只能表示结果未知，不能擅自自动重发保存、删除、发送或回答。

### S07 · 会话名称存在“读取时修改权威记录”的路径

**证据：源码确定＋隔离复现的冲突条件。** [会话库](../lib/session-library.mjs#L10)、[原生列表读取时间](../server/page/agents.js#L207)、[手机元数据合并](../app/js/sheets.js#L79)。

`sessionRows` 在格式化列表时调用 `observeSessionTitle`，可能写盘并广播重命名；某些列表的 `titleAt` 是读取时的 `Date.now()`。如果原生缓存仍是旧名字，却被盖上新读取时间，就可能覆盖刚确认的新名字。隔离检查已确认这种输入下会覆盖；本轮没有把它写成新发生的真实桌面故障。

常用筛选目前使用共享的 `lastMessageAt` 和星标，已经与浏览器打开时间分开。`lastUsed` 等本地记录仍用于排序，不能把这些不同用途的数据全部删掉。

**简化：** 会话库统一管理已确认名称、星标及真实消息时间；列表格式化只读。名称冲突时核实原生真实值／版本，再更新记录，不把“刚读到”当作“刚修改”。迁移旧手机数据单独完成，不让历史兼容合并长期参与每次绘制。

**影响与效果：** 影响列表名称、跨手机常用同步、归档删除后的列表、排序。可减少旧值反复覆盖。必须继续接收电脑端真实重命名，不能让服务端缓存名称永久压过原生名称；不需要逐个打开会话才能确认时间或名字。

### S08 · 自动 Retry 在渲染中安排，调度次数等于点击次数

**证据：源码确定＋隔离复现。** [自动重试](../app/js/chat.js#L207)、[容量提示标识](../server/page/chat-extract.js#L641)。

当前先增加次数，再安排回调；回调发现开关关闭、选择变化或按钮变化会退出。隔离检查中一次未点击的任务已用完 1 次额度，重新开启后不能重试。另一个风险是独立 capacity 提示的合成 ID 只含会话标识，同一会话不同轮次可能复用重试计数键。

**简化：** 容量展示只展示状态；重试控制独立处理。计数属于明确的提示发生实例／原生轮次，在实际执行点击时计数；失败或未执行的调度不消耗点击次数。新轮次不能继承上一轮已用额度。

**影响与效果：** 影响 Codex 自动重试的次数和重新开启行为。保留默认关闭、手动 Retry、次数上限和原生倒计时；不通过反复折叠／展开执行内容来检测容量，不干预桌面自己安排的重试。

### S09 · 通知中的轮次识别和投递状态混在一起

### S11 · 草稿、发送和原生搜索临时输入耦合

### S16 · 缓存清理范围过大，资源发布也不是一个事务

**证据：缓存分支隔离复现；发布流程源码确定。** [SW 激活](../app/sw.js#L16)、[资源列表](../app/sw.js#L2)、[网页资源引用](../app/index.html#L237)、[逐文件发布](../server/publish/pages.mjs#L48)。

3. `syncApp` 逐文件调用 GitHub contents PUT，多个改动形成多次提交，可能出现分批部署。地址发布和资源同步失败的结果也没有完全一致的“本次发布完成”含义。

**简化：** 先把缓存清理限定为本应用旧缓存；再让资源版本与清单来自一个发布来源。一次网页资源更新生成一个提交，地址记录的并发合并独立保留；部署状态与公网文件核对完成后再标记发布完成。

**影响与效果：** 影响离线和网页升级，可减少缓存不一致与发布中间态。会调整发布命令流程；不得重置配对、本地会话和草稿，不得覆盖其他电脑的地址记录。Android `versionCode/versionName` 与 iOS 构建号是独立发布版本，不能强行绑定到网页 `APP_VERSION`。

### S17 · 启动器和 relay 都有隧道生命周期逻辑

**证据：源码确定，结构风险。** [桌面配对入口](../cli/desktop-pair.mjs#L1)、[启动器服务管理](../window_start/pair-link.mjs#L66)、[relay 隧道管理](../server/publish/tunnel.mjs#L120)、[安装检测及启动](../server/launch.mjs#L27)。

启动器管理 relay、查找／启动 cloudflared、读取日志并保存地址；relay 自身也可以做隧道查找、存活检测、恢复和发布。维护两套“何时算可复用／谁负责恢复”规则，容易让不同入口的行为分叉。平台寻找可执行文件、处理 Windows `.cmd` 与 `.exe` 的差异本身有必要。

**简化：** 启动器只确保 relay 被启动，并请求它提供隧道状态；relay 是隧道复用、恢复和地址发布的唯一管理者。平台脚本仍负责发现及启动本机应用，统一机器可读的结果语义；安装检测不承担聊天就绪判断。

**影响与效果：** 影响 Windows／Ubuntu 一键入口、临时／固定地址、后台服务和重启。必须沿用健康隧道，不因 relay 重启就换公网地址；不能关掉用户已有 Agent，不能把端口打开当作项目及会话已可读。需要 Windows 和 Ubuntu 分别验收。

### S18 · 弹窗与全局 UI 修补承担了跨功能清理

**证据：源码确定，结构建议。** [弹窗生命周期](../app/js/sheets.js#L144)、[语言 DOM 修补](../app/i18n.js#L623)、[原生桥接认证](../app/js/auth.js#L4)、[Android 壳](../android/app/src/main/java/com/agentremote/MainActivity.java#L104)、[iOS 壳](../ios/AgentRemote/ContentView.swift#L117)。

`openSheet/closeSheet` 需要知道文件、模型、设备、语音及原生设置的清理细节。语言同时使用显式翻译与全局 DOM 观察修补，维护跳过用户内容的选择器清单。原生壳又以功能是否存在判断不同能力，新增能力需要维护更多跨层约定。

**简化：** 每类弹窗自己注册退出清理；可见 UI 文案逐步在渲染时翻译，减少全局观察器的职责。原生桥接公布小型能力描述，网页按能力使用；不要复制网页业务到两个壳。

**影响与效果：** 影响不同弹窗之间跳转、语言、原生权限和资源释放，收益主要是减少跨模块牵连，优先级较低。不能翻译聊天正文、文件或用户名称。Android 后台 SSE、iOS APNs／Live Activity、原生密钥与存储必须保留，不能为了共用代码而依赖一个后台不会持续运行的 WebView。

### S19 · 旧截图质量链路存在不可能执行的分支

**证据：源码确定＋隔离检查。** [前端 applyQuality](../app/js/screen.js#L69)、[quality 路由](../server/routes.mjs#L369)、[旧 screencast 方法](../server/session.mjs#L370)。

前端先在 `mode === 'screen'` 返回，下一句又在 `mode !== 'screen'` 返回，所有模式都会提前退出。后端同样在两种互补条件中返回，重启 screencast 的尾部无法执行。隔离检查核对了聊天、终端和画面三种模式。

**简化：** 追踪调用后清理确认不再使用的编辑器截图质量分支及相关无效入口，而不是把条件反过来重新启用旧功能。现有 `VisualCapture` 的仿真窗口捕获、缩放、刷新独立保留。

**影响与效果：** 主要减少误导维护的旧实现，不会因为删掉不可达分支就让现有画面更清晰或更快。不能把整个 `screen.js` 或 `Session` 的 frame 处理一起删掉；其中仍有现用的布局、通知帧和模式处理。

## 5. 不建议为了简化而删除的逻辑

以下实现看起来分支较多，但有明确产品或平台目的：

- 请求／选择归属、原生确认、过期回包过滤；否则容易串会话、回填旧草稿和误报发送。
- 首屏缓存只读、历史本地保存与原生历史分页：原生页面有虚拟化，单靠当前 DOM 不足以保留完整历史。
- 实际到底才跟随、打断惯性的一次定位、历史插入一次保位、自由阅读时稳定展示。它们不能被旧阅读锚点替代。
- 两步验证、请求签名、Origin、一次性授权、分组不共享凭据、撤销现有连接、项目信任与路径边界。
- 闲置窗口的终端／后台进程／Agent／Fusion 占用判断及保留最后一个可用窗口。
- 文件传输的同路径串行、有限并发、原子替换、取消清理；PDF／视频的短期授权与 Range。
- 图片编辑的操作记录：裁剪、旋转、撤销、文字移动需要坐标变换，不能只按分支数认定为过度实现。
- 各 Agent 真实数据结构、按钮和审批差异，系统语音／CPU／Qwen 的模型和资源差异，以及 iOS／Android 后台能力差异。
- Fusion 的独立 Runner、阶段确认、停止检查和轮次上限。

本轮也没有发现足够证据要求重写终端渲染、代码高亮、Git 差异解析、扫码、图片编辑和独立 HTTP 文件传输。将它们列入审查不等于必须修改它们。

### 第一批：修确定分支，避免先做大重构

1. S01：补齐 Devin 的原生接受判断，明确 Cursor 的确认契约。

4. S08：Retry 按实际操作计数并区分提示实例。
5. S16：先限定缓存删除范围。

这些是不同功能类别，仍应分别修改和回归，不因为放在“第一批”就一次性混改。

## 7. 用户反馈后的补查：消息漏显与输出抖动

### S20 · Codex 已接受的追加消息被正文提取和回执读取同时漏掉

**证据：真实 Contact_track 会话只读核对＋源码确定。** [原生消息转换](../server/page/chat-extract.js#L254)、[用户消息转换分支](../server/page/chat-extract.js#L281)、[回执读取](../server/page/chat-extract.js#L670)、[原生与可见内容合并](../server/page/chat-extract.js#L722)、[临时消息](../app/js/history.js#L562)、[临时消息末尾插入](../app/js/history.js#L782)。

用户更正：范围是“发送到电脑端的消息有时未显示在手机”，不能限定为排队消息。

在当前真实 Contact_track 会话中，找到 3 条状态为 `accepted` 的 `steeringUserMessage`，其中一条与截图中“另外如果……初筛……”的消息吻合。当前 `codexStoredTurn` 只把 `userMessage` 转成手机的 `user-message`，未处理 `steeringUserMessage`，这 3 条的原生 ID／客户端 ID 都没有进入转换后的用户消息列表。

由此形成一条具体故障链：

1. 电脑已经接受消息，但原生数据转换把它丢掉。生成中直接发送和立即追加均可能使用这种原生类型，与手机上按钮是否叫“排队”无关。
2. `codexReceiptRows` 复用同一转换函数，也读不到它，手机难以把临时气泡与真实消息合并。
3. 临时气泡由 `pendingEchoes` 保存在页面内存中，并在正文所有消息之后插入，没有原生位置，所以会显示在错误的末尾位置。截图中的“正在同步…”与这条分支一致。
4. 临时气泡本身没有写入持久正文缓存；刷新后它消失，而真实消息仍被提取器漏掉，于是看起来消息不见了。**这不是电脑端删除了消息。**

可见原生 DOM 有时已经把消息转换为展示类型，而原生存储仍是 `steeringUserMessage`，两条读取路径因此可能表现不同。不能依赖“桌面上恰好挂载该消息”来恢复手机内容。

**具体修法：** 在现有 Codex 转换处补齐该消息类型及其接受状态、输入内容、原生／客户端 ID；正文和回执复用同一份规范化结果。按原生条目位置写入 `sourceIndex/order`，再通过稳定 ID 替换临时气泡。`steered` 状态事件不再生成第二条同文本用户消息。刷新从原生历史重新读取同一条记录，不靠永久保存临时气泡掩盖漏读。

**影响范围：** Codex 消息提取、接受回执、生成中发送／立即追加、正文排序与刷新恢复；不需要改桌面发送行为、排队策略或其他 Agent。需要验证空闲普通发送、生成中直接发送、立即追加、排队后实际发送、相同文字连续发送、附件及刷新／切回。当前本机普通 `userMessage` 可以提取；不能据此声称用户反馈的所有普通发送漏显都只有这一个原因。

### S21 · 为修手动到底而保留的意图，可能被布局滚动重新使用

**证据：源码与版本差异确定＋隔离复现；未采集用户手机的完整逐帧轨迹。** [意图记录和到底判断](../app/js/history.js#L403)、[程序定位标记](../app/js/history.js#L465)、[空闲收尾](../app/js/history.js#L1440)、[滚动判定](../app/js/history.js#L1466)、[正文延迟绘制](../app/js/history.js#L653)。

`09f44df` 为解决 Safari 迟到的滚动事件，改变了意图清理与校验。具体存在三处逻辑漏洞：

1. `flushSettledChat` 不再清除 `bottomScrollIntent`，手势及惯性结束后仍保留它；`noteChatLayoutChange` 也不再使它失效。
2. `settleChatScroll` 在位置增大时直接把意图的 `top/max` 更新为当前布局值，然后调用 `userReachedBottom`。这里没有要求正在进行用户手势；后续非用户滚动也可能把旧意图更新成“有效到达底部”。此外，反向输入的 `noteBottomScrollIntent(false)` 不主动清空旧意图。
3. 程序回底只用一帧 `restoringChatScroll` 标记。滚动事件如果晚于该帧到达，会被 `settleChatScroll` 标为 `chatScrolling`；正文更新因此进入延迟分支，空闲后再集中绘制。流式更新、程序回底和延迟绘制会互相触发，形成停顿／跳变的条件。

隔离检查已复现：没有活动手势、没有惯性、`chatUserScroll` 为假，旧意图仍能使后续布局滚动开启 `followBottom`；也确认程序滚动标记过期后会进入用户滚动的延迟绘制状态。这证明存在错误分支，不等于已经用桌面模拟完整复现 Safari 的每次抖动。

**具体修法：** 用户到底意图只属于本次手势及其惯性，明确结束；反向输入和不属于该手势的布局变化不能延续它。不得由任意滚动事件刷新旧意图的布局信息来重新授权吸附。程序写位置及其对应滚动事件应有明确归属，不只依赖一个动画帧布尔值，也不能使正常流式输出进入“用户正在滑动”的冻结／补绘路径。吸附仍只在实际到底后开启，已经离底时内容生成不能重新开启。

**影响范围与保留行为：** 影响三 Agent 的聊天滚动、流式绘制、手动到底、最新按钮、上下轮、发送回底与输入框高度变化。保留最新／发送主动回底、上下轮一次定位、手动离底退出、惯性连续、历史插入一次保位；不引入阅读锚点，不在惯性结束后补拉旧位置。应先针对这些明确分支修复，不能把整个滚动器大重写作为本次修法。

补查证据位于 `_shots/logic-audit-v250-20261026/` 的 `message-native-audit.json`、`contact-message-paths.json`、`steering-omission.json`、`supplemental-proof.json`。真实检查仅连接 CDP 读取现有数据，没有发送消息、切换会话或修改电脑端界面；隔离检查不修改产品代码、真实浏览器状态或用户数据。以上两项应排在一般结构整理之前。

## 8. “移除后反而更顺畅”的逻辑：具体含义与边界

这里检查的是某个机制是否为了辅助功能而干扰了功能本身，不以“代码旧”“分支多”或“函数长”定性。应分别记录：还在运行的错误干预、职责耦合候选、没有运行的残留、必须保留的功能逻辑。此前只用三类停用残留回答这一问题，范围不足。

### 8.1 已有具体证据的错误干预

下列路径可以明确指出应停止哪种行为；不是要求删除整个所属功能，也不是已经实施过删改后的完整回归。

| 当前机制 | 停止／移出的行为 | 应保留及影响 |
|---|---|---|
| 手势结束后保留旧到底意图，布局滚动又更新它（B02／S21） | 不再让过期意图授权底部吸附；反向输入、结束后不再复用 | 保留本次真实滑动到底与已开启的底部跟随；解决误拉回的确定分支 |
| 程序滚动一帧后无条件按用户滚动处理（B03） | 取消“没有当帧标记就是用户惯性”的推断，不让回底生成冻结／补绘反馈 | 保留真实惯性期间的稳定展示、显式回底和一次保位；不能直接取消全部绘制控制 |
| 只要 readonly 就展示“正在查看子 Agent 的对话（只读）”（B30） | 移除临时不可操作状态对会话身份的推断 | 保留缓存只读及真实子 Agent 返回入口；此项修正身份展示，不冒充切换失败根因修复 |
| 格式化列表时用读取时间盖过已确认名称（B08／S07） | 列表绘制不因读到旧标题就更新权威名称并广播 | 保留电脑端真实重命名同步；减少旧名反复覆盖 |
| 渲染 capacity 时安排重试并先扣次数（B10／S08） | 渲染只展示，点击计数移到真实执行，不再让重新绘制隐式消耗预算 | 保留用户选择的自动重试、手动按钮、上限和原生倒计时 |
| 配对命令退出依赖地址发布及单一浏览器 exit（B31） | 结束配对不再无界等待无关发布；本次子进程清理有明确结束结果 | 保留固定地址发布、审批和二维码；仅清理本次资源，不退出 relay 或其他浏览器 |

### 8.2 存在反作用可能，尚未做删除对照的活跃机制

| 当前机制 | 可如何减少干预 | 尚需核对的代价及影响 |
|---|---|---|
| 读正文时自动展开／收起原生详情（S04） | 从热路径移出 UI 点击，已有原生数据直接读取；必要隐藏详情按需补全 | 可能晚些取得思考／工具全文；不能删除后假装隐藏内容完整 |
| 打开模型、预读与额度刷新分别操作原生菜单（S10） | 合并同一目标的读取，避免后台反复开关同一菜单 | 需验证缓存时效、菜单恢复及真实选择确认；没有测得确定提速数值 |
| @／/ 搜索暂时替换桌面草稿再恢复（S11） | 存在只读原生索引时直接查索引；否则仅保留一个有归属的临时事务 | 并非所有 Agent 都有可直接读取的搜索入口；不能删恢复逻辑而丢草稿 |
| Fusion 每次进度展示都保存完整历史（S13） | 移出每帧／每段的同步全量保存，阶段／停止／结束仍立即保存 | 减少重复保存调用有隔离证据；真实速度未测，合并保存会改变崩溃恢复粒度 |
| 启动器和 relay 各自管理隧道（S17） | 一个管理者负责复用／恢复，启动器只请求启动和状态 | 必须保持已有健康隧道及各平台入口，未进行 Windows／Ubuntu 删改对照 |
| 全局弹窗关闭兼管多功能清理，全局 DOM 再修补翻译（S18） | 清理由所属弹窗负责，文案在生成处翻译，减少跨功能干预 | 需验证每个资源出口和正文不被翻译；不因职责多就断言当前各处均故障 |

以上候选已在 S 项中登记，不另凑漏洞数。它们说明可以收敛到哪里，尚不能保证简单删除就会更快或完全无影响。

### 8.3 旧残留与必要逻辑分别处理

R01 停用历史空闲等待、R02 回底专用但保留通用外形的补偿、R03 不可达旧画质链路，是已有的三类残留。删停用分支主要减少维护负担，不等于消除所有运行中卡顿。当前没有发现旧阅读锚点继续执行的证据，不把旧锚点作为所有新跳动的统一解释。

选择／请求归属、迟到回包过滤、原生接收确认、历史插入一次保位、底部跟随、认证与权限、最后窗口保留、真实平台差异均有明确用途。可以整理实现，不能先删掉，再为由此产生的问题叠加另一套补偿。

判断简化是否成立，须同时说明移除的行为、替代的事实来源、保留的能力及失败出口，再对受影响场景做前后验证。本轮没有删除这些机制或进行产品改动，因此不将预期效果写成已经提升。

## 11. 新截图揭示的反作用机制

B38 补充了仍在运行、会反向干扰正常操作的逻辑：有草稿未编辑时，在 pointerdown 先扩展布局，以及扩展后统一 400ms 禁止按钮。原本为了展示／防同手势残留，却会影响独立按钮首击；应区分输入区展开与真正动作，不能用更长的延迟或另一层总开关修补。原先 DOM 触发模型成功不等于真实坐标命中通过。

B37 是语义分类被过宽关键词替代：工具命令也可能包含容量关键词。应识别真实横幅所属对象，不能再加“只要没有 Retry 就不显示”的回退，因为真正容量错误也可能没有按钮。B36 将完整横幅文本和动作再次渲染，正文／动作分别读取可直接减少重复。首次 Retry 需要滑动才出现为 Q01，尚未证实具体卡在哪一层，不写成已有唯一简化方案。
