# v295 会话切换逻辑与耗时排查

2026-10-28。只排查，未修改产品代码、发布版本或重启中继。保留当前所有本地修改。阅读 AGENTS.md、本地开发要求及功能基准 02／03／08；复用已有配对 Chrome，不新增配对。实际切换仅 Codex 的已有会话和已打开项目，不发送消息、不停止任务、不创建窗口。Cursor／Devin 仅核对有关源码，Devin、Fusion 不运行测试。

## 当前链路

手机列表点击会话后，发送 `openAgent`；`beginNavigation` 立即标记旧内容不可操作、关闭就绪状态。中继将导航放入现有串行操作队列，取消旧导航／读取，并执行所选 Agent 的项目归属判断。

同项目：读取所选会话项目身份，核对当前编辑器路径与远程主机；Codex 在当前窗口调用原生 `router.navigate`，确认实际会话 ID，再 `adoptCodexThread`，清理旧视图状态、发布绑定身份，等待 `pollChat(true,true)` 首屏。正常路径不切换／新建窗口。Cursor 对应路径通过原生列表定位／点击，再确认活动会话 ID。

跨项目：上述身份读取后进入 `useProject`；查当前／来源／已知／其余窗口，核对真实项目及可用状态，复用已打开窗口；没有可用目标时才启动新窗口。切换 CDP 连接，核对信任／登录／聊天侧边栏，选目标会话，检查项目身份，发布就绪，重建原生监听并等待首屏。

Codex 首屏：`extract` 提取原生记录，等 `codexContext`，合并／裁剪记录，发布给手机，手机收到真实目标内容后结束切换。手机可先显示已有只读预览，最终就绪仍等真实内容。

## 当前实测

证据：`_shots/session-switch-audit-v295-20261028/results.json`。一次四段实际导航，不是统计分位数，也不是 iPhone 真机结果。

| 场景 | 首条目标绑定 | 首条目标聊天回包 | 首次真实内容绘制完成 | 手机渲染耗时 |
| --- | ---: | ---: | ---: | ---: |
| 同项目切另一会话 | 2.786s | 3.069s | 3.085s | 11ms |
| 同项目切回长会话 | 2.636s | 5.499s | 5.526s | 18ms |
| 切到另一个已打开项目 | 19.777s | 28.927s | 28.976s | 41ms |
| 跨项目切回长会话 | 5.608s | 6.017s | 6.042s | 24ms（3次绘制合计） |

只读分段探测：

- 发现两个 Codex 窗口：7ms；项目路径读取：1～2ms。
- 原生会话元数据读取：两次请求分别约 3128／917ms。这是读取请求的端到端耗时，包含原生页面执行排队，不能全部认作查表函数的纯计算时间。
- 长会话 `extract`：1595 条记录、约 1.16MB 原始结果；原生实际提取约 416／421ms，JSON 序列化约 4ms；读取请求总耗时 882／1496ms。首屏发到手机前再合并／裁剪，两个返回长会话的首包约 340KB、472条。
- `codexContext`：本次 9／0ms，不是该次主要瓶颈。它仍是首屏前的串行依赖，换机器、目录或首次读取时可能增加等待。

## 确认存在的可简化环节

### 1. 重复发布绑定，重复强制适配检查

`adoptCodexThread` 普通路径先带状态发布一次，随后又无状态发布；跨项目流程还在 `openBound`／`resumeProjectSwitch` 发布中间和最终身份。手机每收到 `attached` 都调用 `requestCompatibility(app,true,windowId)`，即使电脑、窗口、扩展和会话身份没有相应变化，也跳过已有去重规则重新检查。

实测每段 2～3 条 attached；适配结果也在相邻导航中重叠到达。适配检查使用独立 CDP 读取编辑器与聊天页，虽不在导航 await 链内，仍和首屏竞争同一原生页面执行资源。不能把全部 29 秒直接归因于这一项。

建议：合并冗余的相同绑定通知，保留确有意义的加载／确认状态；自动适配检查跟随实际窗口绑定生命周期，不跟随每次线程身份发布。手动重检保留，不增加固定延时。

入口：`server/apps/codex.mjs:344`、`server/agent/projects.mjs:485`、`app/js/net.js:841`、`app/js/gate.js:162`、`server/apps/compatibility.mjs:7`。

### 2. 首屏先重读较多历史，再裁剪

首屏原生读取与输出预算不是同一个位置：原生先提取较多轮次及正文，返回中继后 `mergeCodexItems` 再保留相应范围；手机显示尾窗不能节省此前提取／传输。这次已测得原生提取本身约 0.42 秒，额外读取与排队也明显高于手机绘制。

建议：将首屏必需的最新轮次／消息范围放到提取入口，较早内容沿现有历史分页读取；保留真实顺序、用户消息与回复边界、生成状态及 capacity／Retry／Question 等当前操作。不能通过丢历史或隐藏必要卡片提速。

入口：`server/agent/chat.mjs:195`、`server/page/chat-extract.js:847`、`server/apps/codex.mjs:229`。

### 3. 切回同一会话也丢掉已完成轮次缓存

`clearViewState` 每次创建新的 `itemCache` Map，已有按 thread 保存的已完成轮次信息一起丢失；再次打开要重新提取。这里有必要清理在途读取、正在生成的状态与旧目标操作，但不等于必须丢掉全部已完成正文。

建议：区分“当前选择的在途状态”与“已有会话数据”，复用现有会话缓存及原生完成轮次身份；首屏仍向原生确认目标和最新运行态，缓存不能冒充实时成功。影响消息合并、旧正文及动作刷新，须一起验证，不额外堆一套缓存系统。

入口：`server/agent/context.mjs:146`、`server/agent/chat.mjs:207`、`server/apps/codex.mjs:229`。

### 4. 跨项目多次核对同一就绪与身份数据

`useProject`、`openBound`、`ensureCodexReady`、`finishProject` 分别读取项目根、信任、当前线程和聊天连接。必要的真实项目、登录／信任和会话成功确认必须保留，但已在本次有效绑定中取得的数据可复用；同一个聊天页内所需的元数据也可用一次快照供本次导航各步骤使用。

建议：把已有窗口复用与新窗口初始化明确分开，已有就绪窗口不重新走完整初始化；新窗口仍等待实际就绪。维持取消、失败回初始页及目标归属；不自动换 Agent、不停止任务，不把普通写操作全部并行。

入口：`server/agent/projects.mjs:197`、`server/session.mjs:225`、`server/agent/projects.mjs:321`、`server/agent/projects.mjs:424`。

### 5. 首屏补充信息与列表刷新

上下文、完整项目列表与模型菜单各有用途，但不是显示目标聊天正文的全部前提。当前上下文读取在首屏前；完整列表与菜单虽已部分后台化，仍会继续占用读取资源，影响紧接着的切换。`codexChatRows(true)` 对每条会话重复取得同一 query client／更新时间，也是可复用的数据。

建议：真实目标正文与运行态先发布，补充信息按原选择异步更新；同项目局部更新当前标记，不为每次切换立即扫描全部窗口。列表的显式刷新与项目展开后聚焦会话必须保留。不要简单增加延时或去掉信息。

入口：`server/agent/chat.mjs:237`、`server/apps/codex.mjs:443`、`server/apps/codex.mjs:42`、`server/page/codex.js:107`、`server/agent/projects.mjs:311`。

## 结论与边界

建议顺序：去掉重复绑定／适配检查 → 限定首屏提取与复用已完成轮次 → 合并窗口初始化重复读取 → 解耦补充信息及局部列表刷新。前两项对同项目和跨项目共同链路生效，第三项侧重跨项目。

这轮已证明手机绘制不是主要等待，但未在生产中给每一个后端函数加追踪，因此不能把跨项目约29秒的样本全部分配给某个内部函数。没有修改判断条件、等待预算、窗口规则或用户功能；没有进行关闭窗口冷启动、远程项目及 Windows／Safari 真机测速。实测完成后原 Codex 窗口／会话及页面就绪已恢复，测试临时函数已撤销。
