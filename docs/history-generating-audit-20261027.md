# Codex 生成中加载更早消息排查

> 后续已按用户确认修复并发布 v276，见 [修复与验证记录](history-boundary-fix-20261027.md)。以下保留修复前的排查结果。

日期：2026-10-27；现场版本：v275。仅排查，产品代码尚未修改。本轮复用原配对 Chrome，只读连接当前仓库正在生成的会话，请求历史后恢复原浏览器选择；没有发送消息、停止任务或新建配对。

## 已确认原因

历史请求的首次游标使用 `Math.max(...orders) + 1`（`app/js/history.js` 的 `requestOlderRemote`），从最新记录向前扫描。初始同步的缓存保留了较早轮次的用户／完成回复，同时裁剪部分明细，所以这个起点会先补回当前展示范围中的明细，不能保证本次请求返回界面顶部之前的消息。

实际配对浏览器复现：

- 生成中，当前 471 条记录，顶部最早可见顺序为 340000（第 34 轮）。
- 发出历史请求的边界却为 650034（第 65 轮）。
- 服务端约 2.23 秒后返回 348 条，最早顺序 550004；手机已合并到 819 条，分页也正常结束。
- 顶部仍是 340000，没有出现第 34 轮之前的消息。不是指令未发出，也不是本次结果被手机丢弃；请求读取的范围不对。

同会话的原生只读检查：当时 65 轮，64 个较早轮次完整存在，0 个缺失、0 个不完整轮次。直接调用分页可返回数据。因此不能把该现场归因于“生成中禁止加载”或当前轮次不完整。

## 浏览器内存试验

仅临时将首次边界改为已加载记录的最小顺序，未改动产品文件。生成中从 340000 请求，约 2.05 秒返回 85 条，手机最早可见顺序变成 300000（第 30 轮），总记录变成 556 条；加载请求和待插入状态均已结束，生成状态仍为 true。结束后恢复原函数和浏览器选择。

该试验证明首次分页边界可以修复这次“有回包却看不到更早消息”的现象，不表示触摸惯性、跨会话取消及所有分页边界已完成修复验收。

## 建议范围（待用户确认）

- 首次“更早消息”请求从当前已加载历史的前沿向前读取；后续沿服务端分页游标继续，保留同一轮分批、去重与身份校验。
- 当前范围内的明细补全不能取代“更早消息”的分页范围。此次不新增定时重试、生成结束等待、持续阅读锚定或另一套滚动机制。
- 修改后用原配对浏览器验证生成中上滑与按钮加载、连续分页、同轮分页、实时新内容、一次性插入保位、切会话取消与非生成状态。
- 影响限于 Codex 历史分页起点及其相关验证；不改变消息发送、生成任务、底部吸附、Retry、其他 Agent 或 Fusion。
