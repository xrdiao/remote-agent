# Codex 强度、发送、加载及连接审查（2026-10-29）

当前网页 v303，仓库 HEAD 为 9991ccb，已有 v300–v303 本地修改均保留。本轮仅排查，没有修改产品代码、发布、重启中继、新增配对或刷新原生 Agent 页面。复用原配对 Chrome；未改原生模型、发送测试消息或停止原任务。用户的第二台电脑及 Safari 现场没有直接连接，本机观察不能冒充这两种现场复现。

已阅读 AGENTS.md、development-requirements.md、基准索引及 01、02、03、04、08。检查以“电脑确认原生结果、手机展示；恢复按电脑＋入口隔离；首屏独立于补充数据；后台连接复用”的既有方案为准。

## 1. 强度已生效却报告失败：写入与回读不是同一来源

确定位置：`server/page/menus.js:192` 的 `pickEffort`、`server/agent/menus.mjs:288` 的 `pickMenu`、`server/agent/context.mjs:187` 的 `waitFor`。

- 写入支持 `codexPickerProps`，也支持 `powerProps` 的 `onSelectPower/onCommitPower`。
- 普通强度列表本身也从 `powerProps.selectedPowerSelection` 读取。
- 写入后的 Codex 确认却只检查 `codexPickerProps()?.reasoningEffort`。原生仅提供 power 控件时，实际强度已经变化，确认仍永远读不到。
- 默认确认预算仅约 1.2 秒，超时返回空并被转换为“思考强度尚未切换”。这里还存在“尚未得到确认”被直接解释成“未生效”的语义问题。

受控运行实际注入 helper 和实际 `pickMenu/waitFor`，原生替身选中 High，最后仍抛出“思考强度尚未切换”。这是确定的源码缺口与受控复现；没有更改用户真实强度来复现。

修复方向：统一强度选项、写入目标和已选值来源，沿实际操作的原生控件确认。电脑保存同一请求的真实结果；读取未完成与明确失败分别反馈，不重复写入，不靠增加多个回读条件或简单拉长等待解决。

影响范围：Codex 模型／思考强度选择和结果反馈，包括 Max 的现有能力判断；保留原有强度、权限和 Fast 行为，不改 Cursor、Devin 的适配逻辑。

## 2. 消息已到电脑，手机仍未确认：回执被整包读取拖住

确定位置：`server/native-windows.mjs:113` 的 `read`、`:163` 的 `registerSend`、`:170` 的 `confirmSends`；`server/apps/codex.mjs:174` 的 `submitPrompt`；`server/page/chat-extract.js:859` 的原生回执读取。

当前已经将提交和原生异步回调分开，并将结果归到电脑端，这是保留的正确方向。但接受确认又被合并进一个大 `Runtime.evaluate`：先 `extract` 正文，再读回执，并读取当前标签、全部 Agent 状态、会话目录；整包成功返回后才运行 `confirmSends`。

- 有在途正文读取时，`registerSend` 调用 `read(true)` 仍直接加入原读取，而该读取可能在注册发送前就确定不读取回执。至少要再完成一轮才有接受证据。
- 正文／目录读取慢、异常或 CDP 超时时，即使原生消息已经存在，也不能及时确认。
- 回执只看最近两轮。观察被拖延且原生又产生多轮时，尚未确认消息还可能已经离开观察范围。
- 提交前读取 baseline 和回执状态也会遍历原生历史绑定；“尾页只返回 80 条”不等于底层查找仅处理这 80 条。

受控检查实际 `NativeWindow.read/registerSend`：已有整包读取不结束时，注册的发送不能确认；整包退出并完成下一轮带回执的读取后才能确认。没有把这项隔离检查当作用户具体消息的现场重演。

修复方向：窗口仍是唯一结果所有者，但接受证据从原生消息／队列更新独立产生，先结束所属发送请求，再独立更新聊天正文／列表。发送时的原生身份与已有消息 baseline 保留，不用正文清空、乐观气泡或按钮点击冒充接收；不自动重发结果未知消息。减少全历史绑定的重复扫描，避免确认循环依赖正文完整读取。

影响范围：Codex 普通发送、Queue、Steer 的接受确认及断线后的结果恢复。三个动作的提交语义不变，不触碰其他 Agent 的提交实现，不以此次修复改变停止功能。

## 3. 刷新／切电脑加载：后台可见状态阻断了显式首屏

确定位置：`app/js/net.js:719` 的 `parkComputerSocket`、`:832` 的 `connect`，`server/routes.mjs:170` 的 `visible`，`server/agent/chat.mjs:156` 的 `pollChat`，`server/session.mjs:38` 的 `setMode`。

离开电脑时会发送 `visible:false` 并保留连接。切回时前端按 `mode → attach → visible:true` 发指令，而这些指令在后端串行执行。首次启用后台预连、恢复目标发生变化或未命中健康 resume 分支时，attach 内的首屏在 `visible:true` 之前执行，`pollChat` 因 `!this.visible` 直接抛“当前会话尚未就绪，请重试”。健康 resume 分支会提前设置 visible，不能把所有跨电脑切换都说成必然失败。

受控使用实际 `Session.setMode/pollChat/ROUTES.visible`，先在不可见状态要求首屏，得到用户同款错误；随后恢复可见。错误是生命周期顺序冲突，不是会话不存在。

与既有方案核对：入口隔离记录、真实项目恢复、失败回初始页和最终导航回包仍然存在；但“后台连接生命周期”和“显式打开必须读取首屏”没有分清，**实现并未完整符合原方案**。正常刷新是新 Session，默认可见，不能只用此分支解释所有刷新失败；它还会受到第 4 项的 Codex 连接／读取异常影响。

首屏还可加入已有共享读取；`fresh=true` 在已有读取时不保证该读取属于本次变更后的快照。是否直接造成某次刷新失败尚未做实际第二台电脑复现，应在修复时按目标身份和读取版本核对，不能靠额外重试掩盖。

修复方向：展示是否可见只控制持续订阅／后台更新节奏，不否决用户明确请求的导航首屏；一次打开用同一目标身份和取消作用域完成绑定及首屏。保留串行写操作、每入口成功记录和失败回初始页，不增加自动切 Agent、替代会话或循环重试。

影响范围：刷新恢复、后台电脑切回、Agent／项目／会话导航的首屏结束与取消。公共连接处如必须调整，只改这段生命周期，不改 Cursor／Devin 原生导航能力；验收需覆盖两者受影响的进入流程。

## 4. Codex Page.enable／持续读取超时：有确定的依赖与生命周期缺口，底层阻塞尚未完整定因

确定位置：`server/session.mjs:285` 的 `openBound`、`:341` 的 `Page.enable`，`server/cdp.mjs:29/61` 的连接与命令，`server/native-windows.mjs:80/113/255` 的共享连接、读取及发现。

本机实际观察：

- 配对 Chrome 停在 Codex Runtime.evaluate 超时状态，未就绪且没有仍在进行的导航。
- 同一 Codex 编辑器目标，简单求值与 Page.enable 约 0–2ms 返回。
- 已映射到可见 Codex 侧栏的聊天 iframe，直接 WebSocket 连接建立，但简单求值、Page.enable、Page.getFrameTree、Runtime.getIsolateId 均在 4 秒检查预算内无回包。不是仅复杂正文提取失败。
- 宿主目标的调试子会话查询最初能读到聊天 wrapper，之后带 helper 的读取及后续子会话简单读取也超时。故不能宣称“换一种连接方式已解决”，更不能直接判定整个 Codex 应用或全部 renderer 已卡死。
- 没有刷新原生页面、暂停／恢复调试器或停止生成来强行恢复现场。

已确认的实现问题：

1. 普通绑定对编辑器和聊天目标都强制等待 `Page.enable`；当前普通聊天没有使用任何 Page 域事件。这是无业务用途的进入依赖，用户的报错正出现在这里。但移除它不能单独解决 Runtime.evaluate 同样不响应的问题。
2. 共享连接的健康仅凭连接 Promise／WebSocket 生命周期维持，命令无响应后仍可被当作健康连接复用；后续 discovery 继续命中同 URL 的共享来源，后台也会继续请求。没有将“传输仍开着”与“可用的原生调试会话”分清。
3. `Cdp` 处理 WebSocket 关闭，但没有处理 Inspector／Target 脱离等协议级生命周期；只删除本地超时请求不会终止目标内已经运行的求值。**本轮未捕获实际 detach 事件，不能断言它就是这次现场的原因。**
4. Codex 历史／回执取数仍有全绑定遍历和多处重复派生；属于需要收敛的成本，但尚无证据把此次最简单 CDP 命令也超时全部归因于它。

修复方向：先去掉普通聊天无用的 Page.enable 前置，梳理 Codex 编辑器、wrapper、实际聊天执行上下文的绑定与解除归属；目标或执行上下文已经变化时释放旧作用域，不复用失效的就绪结论。窗口的共享读取与轻量操作确认分别运行，正文读取失败不阻塞后者或后续导航。需要验证断点是具体调试传输／目标生命周期还是目标内未退出的读取，不能用频繁刷新、延长超时、多个备用连接和静默重试代替修复。

影响范围：Codex 调试目标发现、绑定、监听、正文及回执读取；若需要修改共用 CDP 层，仅限协议连接生命周期，Cursor／Devin 使用者需适当回归，不改两者业务适配。保留原生任务及现有窗口。
