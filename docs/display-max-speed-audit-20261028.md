## 1. 非底部吸附时内容隔一段时间向上挪动

### 已确认的两条显示链路

1. `app/js/history.js` 的 `scMerge()` 按 `SC.show=400` 不断取最新尾部。自由阅读时继续产生消息，显示范围仍向后移动，`syncChildren()` 会删除上方已有条目。
2. `renderChat()` 按整条消息序列化结果重建／更新 DOM，除工具行暂时保留外，没有稳定上方已展示内容几何尺寸的机制。已知消息的高度变化，不一定触发普通快照中的插入保位。

两者均可在 `scrollTop` 不变时让视口中的原内容向上移动。不能靠底部吸附检查；底部跟随会持续写回位置，掩盖几何变化。

### 证据

复用已配对 Chrome，在隔离 iframe 运行**当前源码的 `renderChat()`、`scMerge()`、`syncChildren()` 与插入保位函数**，仅替换无关业务操作和消息正文绘制。所有场景均为自由阅读、关闭底部吸附，不写真实会话缓存：

| 场景 | scrollTop 前后 | 同一个可见条目位置变化 |
|---|---:|---:|
| 已有 420 条缓存，显示最近 400 条；收到最新尾部快照并新增一条 | 1200 → 1200 | 向上 24 px |
| 同样的数据，受控比较时不裁掉头部 | 1200 → 1200 | 0 px |
| 上方已知消息高度 100 → 20 px，普通快照更新 | 1000 → 1000 | 向上 80 px |

这是受控复现，证明代码中的缺口；不能说已逐次还原用户 iPhone 的所有自然位移。

此外，在真实生成中的会话，以滚轮离开底部、确认 `freeScroll` 后分别观察 20 秒与 45 秒，捕获普通消息更新调用 `historyInsertionPosition()`，程序分别将 scrollTop 向上改写约 162／178 px。但被测可见条目的外框位置只变化约 0.1 px，该次确实保住了位置，**不能把它直接归因为用户看到的闪跳**。它说明名为“历史插入”的调整同时参与普通更新，需要与真正历史分页分清，不能直接删除所有历史保位。

本次自然观测期间列表视口高度、输入区高度保持稳定；未抓到 ResizeObserver、输入区动画或底部跟随造成的自然回拉。源码还核对了历史状态条、思考／工具内部滚动、键盘可视区域、图片／Markdown 布局与上下轮位置写入；未将未复现的候选写成已证实原因。

### 建议修复

- 自由阅读期间固定已展示消息范围，不因新消息持续裁掉其上方旧条目；新数据继续接收，按当前阅读范围更新未展示数据。
- 稳定已完成内容的 DOM 与几何尺寸，避免仅因元数据、阶段状态变化重建正文；对会改变上方高度的数据更新，按阅读显示范围安排应用，不能直接改动视口上方布局。
- 真正的历史插入保留一次性保位；普通消息更新不再与历史插入混为一条处理路径。
- 不引入持续阅读锚点、惯性结束后的旧位置补偿，也不通过强制底部吸附遮住位移。

影响限于聊天显示范围、消息 DOM 更新、历史插入的交接。必须回归自由阅读中的生成更新、400 条边界、真实顶部分页、历史插入保位、最新按钮及手动到底；不改消息收发、原生任务或历史数据存储。

## 2. 新项目 Max 切换报“Codex 设置内容尚未加载”

### 已确认根因

`server/agent/menus.mjs` 在每次选择 Max 时无条件调用 `enableCodexMax()`；后者强制打开 Codex Settings，再进入 Configuration 启用隐藏强度，最后才调用正常的原生强度切换。

但是新项目的模型能力与原生设置编辑页有独立初始化生命周期。设置页的 CDP 目标和 HTML document 已连接／complete，不代表设置应用的侧栏及配置数据已加载。`withCodexSettings()` 用固定 `[data-appearance] button.sidebar-item` 条件和独立的约 5 秒轮询期限判断失败，新项目加载及后台调度超过此期限就报错。

### 实际复现

- 新项目原生模型属性已经包含 Max，当前强度 high；手机也可以列出 Max。此时再次进入设置页并非切换 Max 的必要步骤。
- 普通新项目首次读取设置约 6.2 秒，再次读取约 47 ms。
- 最小化的新项目，初始化初段曾报“没有找到 Codex 设置菜单”；随后同一新项目控件已出现，再读设置：首次约 **8.555 秒**，复现 **“Codex 设置内容尚未加载”**。当时 iframe 与 HTML 均 complete，但设置应用内容尚未出现。
- 同一窗口随后再读约 **1.510 秒** 成功，原生侧栏、General、Configuration 等数据正常。不是模型不支持 Max，也没有证据表明必须更换插件版本。

未实际切换 Max、未勾选或更改任何原生设置；本次验证的是导致 Max 失败的强制前置设置链路。

### 建议修复

- 先读当前项目当前模型的实际可选强度。原生已包含 Max 时直接使用正常切换及读回确认，去掉强制打开设置的冗余前置步骤。
- 仅当模型支持 Max、但该选项尚未启用时才进入配置启用流程；等待本次真实设置数据就绪，不用“模型已加载／页面已连接”代替设置就绪，也不靠重复打开或增加一段固定延时修复。
- 保留原生强度读回、不支持模型的真实反馈、其他强度及原生配置恢复行为。

影响限于 Codex Max 启用、设置页就绪及强度切换确认。回归新项目／原项目、已启用／尚未启用 Max、连续切换及后台项目窗口；其他 Agent 的强度、模型、Retry 不改。

## 3. 模型、Fast／思考强度载入慢

### 源码与实测

`readMenu('effort')` 依次执行强度、Fast 状态和完整 `extract()`；模型菜单也在读取选项后额外执行完整聊天提取，只为取得模型名。每次 helper 调用还要经过 CDP 执行。这让简单参数读取依赖整段聊天解析。

本机对真实当前会话只读分段测量：

| 操作 | 适配器耗时 | 其中整段聊天提取 |
|---|---:|---:|
| 模型菜单 | 1.431 秒 | 0.912 秒 |
| 思考强度／Fast 信息 | 2.581 秒 | 0.790 秒 |

既有配对浏览器未命中菜单缓存时，点击到回包实测模型约 **3.836 秒**、思考强度约 **4.538 秒**。请求发出本身不到 1 ms；服务端日志也记录了两次 `openMenu` 执行各约 3.49 秒。因此至少有可归因于软件读取实现的耗时，不能全归为网络。

`requestMenu()` 未命中缓存时只改底部状态文字，直到回包才打开菜单；从模型菜单进入强度列表时也会暂留原列表，没有就地加载反馈。实测即时菜单加载提示不可见。这又造成“按了很久才有反应”的观感。

普通请求还共用串行队列，前面的未完成操作可能增加等待；本轮没有将所有请求的队列等待单独量化，不能把全部剩余耗时归为队列。

### 建议修复

- 使用当前原生模型选择属性一次读取模型名、强度选项和 Fast 状态；菜单链路去掉完整聊天提取，合并不必要的重复 CDP 往返。
- 保留当前项目／会话及请求归属的缓存语义，不把其他项目或旧请求的选项混入当前列表。
- 首次点击立即显示当前菜单的加载态，收到真实结果后填充；Fast 点击提供等待反馈，实际状态读回后再确认成功。
- 首先修正上述确定的读取与反馈问题，不为该项重写所有请求队列或改动无关读写功能。

影响限于模型／强度／Fast 菜单取数、缓存刷新与加载反馈，不改变模型能力、费用、实际生成速度或服务商延迟。

## 2026-10-28 按确认方案实施与验证

### 实际修改

- **显示稳定性**（`app/js/history.js`、`chat.js`）：初始尾窗仍为 400 条，自由阅读时保留已展示的行，不随快照裁头；阅读区域及其上方的正文变化和新插入明细先保存到既有数据缓存。显式展开、历史插入和回到底部再提交相应正文，不在惯性结束后回拉。按钮、子 Agent 入口及 live 状态独立更新，不为这些元数据重建正文。普通流式快照不再执行通用插入保位，显式历史仍保留一次性调整；没有新增持续阅读锚点。

- **参数菜单**（上述 menus、`app/js/sheets.js`、`core.js`、`notify.js`、`net.js`、`server/routes.mjs`）：Codex 参数通过一次 CDP 读取原生选项、当前模型和 Fast，不再为模型名调用完整聊天 extract。冷缓存立即显示加载面板；Fast 显示等待，读回原生结果才改变开关，失败恢复可操作。沿用现有请求身份与选中目标过滤。新增的加载面板对应补齐菜单失败回包、空结果和未发出时的结束显示。

自由阅读可能暂时保留超过 400 行，回到底部后回收；部分正文补全等待用户显式操作，但最新数据、运行态和操作信息继续接收。没有改发送、项目恢复、通知、PDF 或 Fusion 的实现，也没有进行 master/debug 的提交或推送。
