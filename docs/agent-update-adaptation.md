# Agent 软件与插件更新后的自适应方案

日期：2026-10-27。实现基线：`0a80c53`，保留本地尚未提交的 Windows 兼容性修复；未整批合入已回退的远端提交。

**状态：第一阶段初版已实现，验证范围见文末。** 目前提供版本识别及输入入口、模型数据、会话标识三项只读检查；完整能力覆盖、未知结构自动修复及第二、三阶段尚未实现。本方案不授权安装、升级 Agent 或修改用户设置。

## 目标与边界

Cursor、Devin 或 Codex 插件更新后，RA 应识别环境变化，判断各项功能实际是否可用，复用已经验证的适配方式，并准确报告不能适配的部分。

能够自动处理的变化包括从原生列表取得的新模型、模型名称和选项，以及按实际进程定位的安装位置。页面结构、内部数据字段或操作流程发生实质变化时，仍需更新相应的 RA 适配器，不能承诺任意新版本都无需人工修复。

Ubuntu 原有功能优先。适配修改限制在对应 Agent 和平台边界，不附带调整聊天同步、历史、项目导航、文件传输或其他性能优化。已经运行的任务不因版本检测被停止、刷新或重新发送。

## 一、准确识别版本

- Cursor、Devin 分别记录软件版本。
- Codex 同时记录 VS Code 版本和 Codex 扩展版本，不能用其中一个替代另一个。
- CDP 的浏览器内核版本只描述连接环境，不代表原生业务结构已兼容。
- 版本信息来自实际目标应用、安装元数据或所属扩展，不根据显示名称猜测。
- 区分成功读取、暂时未读到和明确不支持；未知版本不能冒充已验证版本。

版本识别仅用于选择及解释适配结果，不修改 Agent 的更新渠道、安装目录、账号或模型设置。

## 二、按功能进行只读能力检查

识别更新后的流程为：版本读取 → 检查当前目标结构 → 选择已验证适配方式 → 汇总各功能状态。

分别判断聊天读取、发送入口、项目／会话、模型／强度、权限／审批、额度及附件的适配情况。只读检查确认的是数据或操作入口能否识别，不等同于已经实际发送、保存、批准或切换成功。

状态应区分已识别、尚未就绪、原生不支持和适配失败，不能把尚未挂载的页面、未登录、工作区未信任或暂时断线统称为版本不兼容。

检查时机限于首次绑定、软件或插件版本变化，以及重新连接或目标变化后必要的状态核对。复用仍适用的结果，不加入高频轮询，不反复打开菜单、滚动页面或刷新 Agent 来完成探测。确需打开菜单读取的能力，沿原有用户操作入口验证，并保留原生界面归属。

## 三、沿现有适配器处理变化

1. 优先使用已有、含义明确的原生数据字段、稳定属性及控件角色，不把坐标或某段显示文字当作长期业务身份。
2. 模型、强度及权限选项来自当前原生列表，保留原生值、选中状态和实际语义；不因名称相似就自动映射成另一个选项。
3. 有明确结构特征且已验证的实现可以继续使用。版本号辅助定位，不能成为判断兼容性的唯一依据。
4. 确需保留版本差异时，记录对应结构、适用范围及验证证据；不不断叠加猜测式回退。结构无法确认时报告具体失败点，不静默改用另一项目、会话或文件。
5. 复杂变化通过修改对应适配器及正常 RA 发布流程交付。本方案不引入运行时自动生成补丁或下载执行未知适配脚本。

例如，Devin 的会话标识变化应在 Devin 的会话读取及相关操作中统一处理，不让其他 Agent 的会话身份规则跟着变化。

## 四、缓存与结果归属

- 检查结果属于具体电脑、Agent、软件／插件版本及适用的原生窗口或会话环境。
- 版本变化使对应能力检查结果失效，不清空配对、草稿、聊天历史、星标或用户设置。
- 切换电脑、Agent、窗口或会话后，旧检查结果不能覆盖新目标；仍适用的软件级结果可复用。
- 显示原生选项不代表写入成功。发送、模型切换、权限调整和审批仍核对对应请求的真实原生结果。
- 软件更新不自动终止进行中的任务；结果未知时不自动重发、重试保存或批准。

## 五、明确反馈与隐私

手机端应说明失效的具体功能及已知版本，例如“当前 Devin 版本的会话列表暂未适配”，避免只显示“连接失败”。仍然正常的功能保留原有入口和交互。

权限模式、审批目标或发送目标无法确认时，不显示操作成功，不擅自采用更宽松的授权方式。能力检查不替用户作出授权决定。

诊断优先只记录版本、结构特征、功能状态、错误类别及必要的匿名标识。不得收集或公开消息正文、文件内容、令牌、密钥、配对链接及账号凭据。必要证据在本地脱敏保存；截图及临时产物按仓库约定放入 `_shots/`，不随代码提交。

## 六、实施顺序

| 阶段 | 交付内容 | 范围约束 |
|---|---|---|
| 第一阶段 | 版本识别、最小只读能力检查、具体失败报告 | 不改变现有业务操作；先让更新后的问题可定位 |
| 第二阶段 | 将已确认失效点接回各自适配器，补齐结果归属 | 只处理实际发现的结构差异，不批量重构 |
| 第三阶段 | 记录经过验证的适配范围及回归证据 | 不仅凭版本号判定所有功能正常 |

每个阶段需单独明确实施范围并取得用户确认；本文本身不表示已授权实现全部阶段。

## 七、验证与验收

按修改范围读取 [功能基准索引](baselines/README.md) 及相应基准，重点关联 [项目与会话](baselines/03-projects-sessions-windows.md)、[原生交互](baselines/04-native-controls.md)、[连接与配对](baselines/08-connection-pairing.md) 和 [客户端交付](baselines/09-client-delivery.md)。

验收至少区分以下情况：

- 现有已支持版本保持原有行为；新增模型或名称变化来自真实原生列表。
- 已验证的新结构选择正确适配器；未知结构报告准确，不伪造成功。
- 断线、未登录、工作区信任和页面未挂载不会被误报成版本不兼容。
- Windows 与 Ubuntu、三个 Agent 的修改及受影响功能分别验证，不用单平台结果代表全部平台。
- 版本或目标切换后，迟到结果不串目标，已有历史、配对与任务不被清理。
- 按仓库要求运行 `npm run check`，并在用户授权下用已配对浏览器验证实际受影响流程。

只读检测、隔离检查、浏览器交互和真实操作结果分别记录。没有软件、对应版本、平台或浏览器时标记未验证，不把源码分析或端口连通当作功能验收。

## 本次实施与验证边界
