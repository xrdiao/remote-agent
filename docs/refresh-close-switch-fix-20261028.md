# 刷新首屏期间关窗阻塞切换：修复与验证

日期：2026-10-28（北京时间）。Ubuntu、Node.js 22、既有配对 Chrome；起点网页 v288，交付 v289。保留原有本地修改，未回退或覆盖其他功能。用户授权限定修改本次第三点的补充场景，并简单复核第四点 Cursor；发送、历史分页两个独立异常及 Fusion 不在本次修复范围。

## 结论与根因

旧导航虽然收到取消，串行命令队列仍要等待旧 `handle` 返回。`pollChat` 返回的首屏 Promise 没有接入取消；首屏还可能加入没有导航信号的后台读取。后者在读取／补充界面详情时占用 `chatUiDetails`，单独结束首屏等待仍不足以让新导航的聚焦操作继续。

Codex 发布首屏前等待共享的 `codexContext`，该等待也没有响应导航取消。窗口 CDP 关闭时，旧实现只解绑并发送普通 status，既没有结束首屏 Promise，也没有明确结束前端导航加载。以上是源码和受控执行确认的取消／资源生命周期缺口，**不表示已经证明自然故障一定发生在上下文磁盘读取较慢时**。

用户给出的旧证据 `_shots/refresh-close-switch-audit-20261027/controlled.json` 在当前工作区不存在，本轮没有假称读取过它；另行重建受控证据。

| 文件 | 改动 | 行为边界 |

## 第四点：Cursor 简查

按实际编辑器目录找到自有 Cursor 测试窗口，读取原生会话 ID，通过发布页切换两条已有会话，分别约 819／918 ms；原生选中 ID 与手机一致，同项目保持当前窗口。最终简查通过，没有修改 Cursor 适配器／项目匹配实现。原先普通工作区窗口与 Agents 项目不一致的判断在本轮未被证实为当前故障；本轮没有覆盖独立 `Cursor Agents` 窗口的全部跨项目路径。

早先两次脚本等待用了不存在的 `currentThread` 变量，形成假超时；纠正为 `currentComputer().threadId` 后重新执行通过。原记录保留，明确作为测试脚本问题，不计入产品失败。见 `browser.json` 最后一项及 `cursor-fourth-status.json`。
