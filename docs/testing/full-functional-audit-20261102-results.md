## 未通过项与根因证据

### RA-01：漏过 running 快照时，新完成轮次不生成主页完成标记（已获准修复）

真实场景：专用 Cursor 会话提交短回复后立即返回主页。原生新轮次已返回 `completed`，主页持续为 `idle`；另一个已停止会话仍正确显示停止。

当前 [overview.js](../../app/js/overview.js) 的 `ovApply()` 仅在“上一快照与当前 run ID 相同，且上次状态为 running”时写入 `ovDone` 并调用完成通知。受控调用**当前实现**得到：直接从旧 completed 轮次到新 completed 轮次没有标记／通知；中间插入同 ID 的 running 快照则二者均产生。

这证明状态判定依赖中间采样；真实用例是否正好漏过该快照，还需补齐对应原生快照序列。已确认原生完成与主页空闲的不一致，不是仅凭加载慢推断。

- 影响：普通主页完成徽标及通知；短任务、快速返回主页、恢复时漏过中间状态的场景需要重点验证。混合完成状态排序与打开确认测试因此受阻。
- 实施范围：用户确认后仅在 `app/js/overview.js` 调整完成轮次识别及基线，保留“未知／失败／停止不算完成”；具体差异、测试和加载版本见文末本次实施记录。
- 证据：`card-completion-real.log`、`card-completion-scene.json`、`card-completion-controlled.json`。

### N-02：Codex 排队请求停在确认，原生保留未发草稿（提交时序已修复）

真实用例中第一条普通请求被接受并完成；第二条通过现有“改为排队”入口提交。20 秒后原生队列为空，第二条没有进入用户消息，原生输入框仍保留全文；RA 同时保留一条 pending send 和“正在确认电脑端接收…”。

首轮定位到原生未接受第二条请求，未观察到网络断连或页面脚本异常。后续使用不同测试标记复现同类故障，并通过原生条件断点捕获真实提交状态；没有重发最初的未确认请求，也没有把输入清空或伪造回执。本问题与 C1 的“已接受后恢复已发草稿”分开记录。

原生第一次提交在 `1793624576460` 进入时 `submitting=false`；约 410ms 后的 Queue 回调中，`submitting=true`、`responseInProgress=true`、`submitDisabled=false`、`canQueueFollowUp=true`，并保留暂态 `empty-message` 阻止原因。安装版本的实际提交函数在入口执行 `if (... || s.get(tm)) return;`，因此第二次调用命中“仍在提交”条件直接返回；它不会抛出异常，也没有产生队列项。RA 仅串行完成了“分发回调”这一步，先前原生异步提交仍未结算；回调的正常返回也没有为未接受请求提供失败回执，所以手机一直保留待确认。

另一个独立对照在原生已稳定忙碌后入队成功，队列出现 `RA_QUEUE_LOCATE2_B_20261102`。实际控制条件、队列和原生消息把问题缩小为提交阶段的竞争；不需要以断网、账号或 C1 解释这次已捕获的退出。最初旧请求没有当时的函数轨迹，不能倒推它只可能有这一原因。

- 影响：该场景的排队发送及其后续编辑／删除／停止验收；不代表三次普通发送或 `/compact` 未通过。
- 已确认并实施：在 `server/agent/chat.mjs` 的 Codex 发送入口复用已有 `codexViewState(true)`，上一笔提交结算后才聚焦、写入本次发送正文及执行 Queue／Steer。等待沿用发送取消信号，结算后核对原 CDP 和会话归属，不增加定时延迟、重发或扩展补丁。普通 `setDraft()` 不增加结算等待：原生允许提交期间编辑下一份草稿，且普通草稿路由没有发送取消信号，把等待放在该处会额外阻塞停止及切换。实际验证见文末第 2 项。
- 证据：首轮 `queue-stop-real.json`、`queue-native-comparison.json`；本次 `_shots/completion-fix-20261102/codex-queue-trace-3.json` 为捕获原生退出条件的有效轨迹，`codex-queue-trace-2.json` 为成功入队对照。较早两份条件断点日志用了外层窗口读取数组，未取到 iframe 的记录，不据此裁定回调没有执行。
- 旧专用窗口的原草稿摘要在每次定位后相同；原配对标签中最初那条未确认请求仍保留。
