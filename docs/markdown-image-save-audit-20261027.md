## 1. Markdown 未进入真实回复渲染路径

已按用户截图对应的“已修复并发布 v276”完成回复核对实际回包与渲染，不再用手动补充来源字段的夹具代替。

| 核对项 | 实际结果 |
|---|---|
| 当前 Agent | Codex |
| 回复的 src 字段 | 不存在 |
| 回复 HTML | 等于原文转义加换行的纯文本回退 |
| 正常 renderItem / 当前元素 | 0 个 strong、0 个 code、0 个文件引用入口 |
| 同一真实回复直接交给 codexReplyHtml | 正确生成 1 个 strong 和 1 个文件引用入口 |

根因：`app/js/chat.js:277` 仅在 `it.src === 'codex'` 时使用 Markdown。Codex 助手回复的正常提取并不提供此字段，所以真实数据始终走原有 `it.h` 分支。`src` 仅在部分工具／适配内容上存在，不能被当作所有消息都有的 Agent 身份。

此前验证的缺口：Markdown 浏览器夹具手动设置了 `src: 'codex'`，解析器和这条人工条件下的分支通过，却没有验证真实回包能进入分支。真实完成回复 Copy／Fork 保留检查也不能替代 Markdown 端到端验证。此前把该结果概括成实际 Markdown 已修复不准确。

建议：助手正文按当前会话已经确认的 Agent 身份选择渲染器，不新增消息字段或缓存迁移分支。保留原生富文本优先、原文复制、数学／代码／文件入口；不改工作过程、工具、Question 或 Retry。

## 2. 图片保存等待 HTTP 上传，阻塞编辑器关闭

在自有 Codex 测试项目创建测试图片，通过真实图片编辑器旋转，再实际点击保存。完成后删除测试附件，恢复原浏览器选择。

样本：1400×1000 噪声 PNG，旋转后仍用原参数处理为 714,303 字节 JPEG。

| 阶段 | 实测 |
|---|---:|
| 编辑 PNG 导出 | 33 ms |
| JPEG 编码 | 13 ms |
| shrinkImage 调用 | 15 ms（包含上述 JPEG 编码，不应重复相加） |
| 点击保存至开始 HTTP | 56 ms |
| HTTP 上传请求等待 | 11,446 ms |
| HTTP 返回至编辑器关闭 | 3 ms |
| 点击保存至编辑器关闭 | 11,505 ms |
| HTTP 返回至原生附图回执 | 1,038 ms |

根因链：`image-editor.js` 的保存循环等待 `attachImageFile`；后者在二进制传输改动后等待 `uploadDocument` 完成 HTTP，才返回“加入上传”。编辑器因而在整段网络请求期间保持保存中。耗时主要不在本地导出，不能用降低质量或改编码参数来代替修复。

当前路径已经在“电脑原生附加完成”前关闭编辑器，界面文案本来也表示“图片已加入上传”；问题是本地保存／入队与 HTTP 传输没有分开。

建议：本地编辑结果被附件上传流程接收后返回，传输留在附件流程中继续，真实完成由既有 imageDone 回执确认。复用现有 imageUploads、进度、失败重试、取消和目标归属；保持原生图片替换完成后才移除旧图，上传未完成仍按既有规则阻止发送。上传任务按入队顺序执行，不能因改为后台传输把多图顺序打乱。不新增定时器、重试层或兼容分支，不改尺寸／质量及文档上传。

这解决的是软件把网络等待绑定在保存界面上的问题，不承诺公网传输本身变成固定耗时。
