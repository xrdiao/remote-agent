## 结论

发送卡在“发送结果待确认”存在明确的生命周期缺口：已经提交到原生应用的确认观察，仍由手机 WebSocket 的 Session 管理。手机连接销毁或收到停止指令时，这个观察会被取消；手机重连后没有请求结果恢复，Codex 又不再从手机聊天快照认领回执，因此真实消息已接受也可能一直显示待确认。

这不等于已经证明截图那次操作发生了暂停或断线。现有配对 Chrome 没有该待确认记录，不能替代截图手机的事件证据。

“手机后台”与“停止任务”须分开：`visible:false` 只停止该手机的聊天展示订阅，本身不取消原生接收确认；连接随后断开才进入 Session 销毁。停止指令则在检查电脑原生停止按钮之前，就清除了已提交发送的确认观察。

## 已核对的功能与归属

| 功能 | 当前实际执行与确认 | 缺口及影响 |
| --- | --- | --- |
| Codex 普通发送、排队、立即追加 | 中继点击原生对应提交入口；共享窗口从原生消息／队列认领接收事实 | `server/apps/codex.mjs` 将回调及取消句柄绑定到原 Session；`Session.dispose()` 取消观察，结果不能跨连接恢复。电脑实际接受与手机最终显示脱节。 |
| 主任务停止 | `server/agent/chat.mjs` 检查并点击原生停止按钮；运行状态仍由原生更新给出 | `server/ws.mjs` 收到 stop 就先取消已提交发送的接收观察；未检查原生是否有停止按钮。手机按现有要求清理待发送展示，与电脑保留真实接收事实不能混为一件事。 |
| 手机后台／断线 | 后台隐藏停止展示订阅；断线释放 Session | 可见性变化本身不删除回执，但断线会。不能要求手机页面一直运行，才能完成电脑端业务确认。 |
| 自动 Retry | 电脑执行 click 并返回 clicked；手机 `syncCodexAutoRetry()` 决定何时点击，Map 保存成功点击次数 | 自动化生命周期及次数随页面消失，多个入口分别持有计数。重复触发是代码结构上的风险，本轮未触发真实容量错误复现。手动 Retry 不应由此改成自动审批或默认开启。 |
| 模型／思考强度／加速设置 | 电脑执行并回读原生设置，之后回传 `menuPicked` | 并非全部确认都在手机做；结果只发给当时连接，缺少原请求结果恢复。保留已有原生回读，避免再叠加手机轮询。 |
| 队列编辑、问题回答、请求操作 | 电脑执行，返回 `queueDone`／`questionDone` 等 | 回复通过当前 Session 发出；连接断开后没有统一的结果查询／恢复。不能因为手机没收到回包就重新提交。用户审批决定仍由用户作出。 |
| 会话重命名、删除／归档、批量操作 | 电脑执行并确认，列表变更也会发布；批量进度放在 Session | 批量循环以手机连接及当前 Agent 为继续执行条件，进度随视图存活。后续迁移应保留既有取消规则，不能未经确认把删除改成断线后继续执行。 |
| 文件保存 | 电脑完成写文件后返回 `saved` | 手机保留单次保存等待，超时／断线只能显示结果未确认；实际已保存也可能丢失回包。不应重写已有文件写入逻辑来处理这个生命周期问题。 |
| 子 Agent 停止提示 | 手机发送 subagent 指令后立即显示“已停止子 Agent” | 尚未收到电脑结果就宣告完成；属于手机提前决定业务成功。仅源码确认，未停止真实子任务。 |

源码入口：`server/ws.mjs`、`server/session.mjs`、`server/native-windows.mjs`、`server/apps/codex.mjs`、`server/agent/chat.mjs`、`server/routes.mjs`、`server/agent/menus.mjs`、`server/agent/session-actions.mjs`、`server/agent/files.mjs`；前端对应 `composer.js`、`chat.js`、`history.js`、`sheets.js`、`files.js`。

## 受控检查

证据：`_shots/codex-receipt-audit-20261029/controlled.json`、`stop-visibility-ownership.json`。隔离环境复用当前窗口回执实现及实际停止清理代码，不操作真实 Agent。

- 仅隐藏手机页面后，原生消息到达：接收回调执行一次。
- 执行现有停止前置清理后，原生消息到达：观察记录为 0、回调为 0；此时尚未执行原生停止操作。
- 执行真实 `Session.dispose()` 后，原生消息到达：观察记录为 0、回调为 0。
- 手机保留结果未知的发送后，提供原生聊天消息：Codex 手机端不补认，待确认仍为 1。

这证明这些清理路径会丢失确认，不能证明截图手机具体经过哪条路径。没有对真实 Safari 后台断线、多个入口自动 Retry 或真实文件保存断线进行现场验收。

## 后续修改方向（未实施）

1. 在现有电脑端共享窗口／业务执行位置管理请求及结果，以请求 ID 关联入口、电脑、Agent、窗口和会话；已提交任务及最终事实不随手机展示连接销毁。手机提交意图、订阅状态，重连读取同一个请求结果。只恢复结果，不重新执行消息／审批／删除／保存。
2. 停止时取消尚未执行的发送步骤，按既有规则清理手机待发送记录，并检查／点击电脑停止按钮；已交给原生的发送继续按真实接收事实结束确认，不能把取消等待当作撤回。点击停止与原生已经空闲分别如实呈现，不增加两套暂停按钮。
3. 原生确认已在电脑端完成的功能保留原确认逻辑，只调整结果归属和恢复；子 Agent 停止提示等待电脑结果。自动 Retry 的自动化与次数归电脑端，保留用户开关、上限和真实点击结果，具体入口共享规则实施前明确。
4. 手机继续负责草稿编辑、文件选择、渲染、翻页及耗时格式化；原生接收、执行、设置生效和运行结束的事实来自电脑端。只读展示请求仍可随页面取消，不把所有读取变成常驻业务任务。

需要用户确认具体修改范围后实施。影响发送／停止和上述操作的结果生命周期，不授权改动功能语义、Fusion、其他 Agent 接口或无关优化。
