## 1. 结论和证据边界

**当前登记 38 项有具体错误路径的问题，涉及消息、滚动、异步请求、会话管理、通知、Fusion、文件、配对、缓存和平台入口。** 其中一部分需要特定失败、切换或并发条件，并非每次使用都会发生。B31 为配对退出补查；其 Windows 条件采用当前源函数隔离验证，没有 Windows 真机。B32–B35 为后续全功能验证补入，见第 16 节。

**覆盖纠正：此前完成的是各功能入口、主要调用链及部分失败分支的审查，不是全部代码分支及跨功能组合检查完成。** 用户后续指出的 B30、B31 说明具体分支确有漏查；不能用“20 个功能域都有条目”代替检查深度。明确漏查项、只读未验证项和未执行项见第 13 节；未审尽的部分不标为无漏洞。

Windows 路径、命令查找、编码和平台接口的后续专项见 [Windows 兼容性排查](windows-compatibility-audit-v250.md)。本文 B01–B38 是按具体触发链登记的 B 清单，不是包含后续所有专项的总数；W 分组及平台能力缺口没有直接相加。

用户指出的两个问题确实有具体逻辑缺口：

- **电脑已接受的消息仍可能不显示在手机上。** Codex 的 `steeringUserMessage` 没有进入当前统一消息与回执读取；本地临时气泡则放在当前列表末尾，刷新后丢失。该原生类型不等于“排队消息”，不能只修排队按钮。
- **输出时抖动和误吸附。** 旧向下滑动意图未结束，布局产生的滚动又可能被算成用户到达底部；程序滚动的标识只有一帧，迟到的滚动事件还会被算成用户惯性。这是两条需要分别处理的路径。

证据分为：

| 标记 | 含义 |
|---|---|
| 原生对照 | 已读取真实原生会话并与当前提取结果对照，不发送消息或修改原生界面 |
| 隔离复现 | 执行当前源函数，控制输入、时序、返回值或临时文件；不是重写一个相似算法 |
| 源码确定 | 可以沿当前调用链确定错误分支；平台项未冒充真机复现 |
| 配对浏览器 | 在真实已认证网页使用正常界面控件，记录对应场景；本轮为 Ubuntu Chrome，不等于手机或 Windows 真机 |

核对方式：按功能入口检查主要成功路径及选定的失败、取消、切换、刷新和断线出口；没有穷尽每个入口的全部分支。已有证据复用，不对同一处反复扫描。初轮 13 项、补查 4 项检查复用；首批新增 21 个定向检查。**这 38 个检查不是 38 个独立漏洞**，其中包含反例、同一漏洞的多个分支和结构分析。B30、B31 的后续定向证据另列，不把检查数量写成覆盖率。

本报告覆盖本仓库自行实现的功能与适配逻辑，不审计第三方压缩库、操作系统和 Agent 本体的实现。不把“未发现新增问题”写成数学意义的无漏洞证明。Windows、macOS、Android、iOS 的平台项均标明验证层级。

## 3. 消息与滚动

### B01 · Codex 消息漏读、临时气泡位置与刷新丢失

位置：[原生消息归一化](../server/page/chat-extract.js#L254)、[回执读取](../server/page/chat-extract.js#L670)、[临时气泡合并](../app/js/history.js#L782)、[发送状态](../app/js/composer.js#L21)。

触发：Codex 接受的用户消息保存为 `steeringUserMessage`。真实 Contact_track 会话中，第 7、9、21 轮有这一类型；当前原生数据存在，而归一化用户消息中缺失。第 21 轮与用户截图中的补充消息匹配。普通 `userMessage` 已有读取，不应因此声称所有普通发送都必然漏显。

原因：存储读取只处理 `userMessage` 等已列出的类型，未知类型返回空；回执共用这一读取。前端气泡在内存中暂存，并附在当前已显示内容末尾。原生消息长期不能被认领，便表现为位置错误／正在同步；刷新后临时气泡消失，原生提取又仍漏读。

最小修复：在现有归一化入口补齐该原生用户消息及稳定 ID、原生顺序和正文，让历史、实时内容、回执共用结果；区分真正用户消息与重复的状态事件。临时气泡按原生归属认领，不能用永久保存假气泡掩盖原生漏读。

影响：Codex 生成中发送、立即追加、接受确认、顺序及刷新恢复。Cursor、Devin、排队执行策略不需要随之重写。

### B02 · 旧向下滑动意图可被流式布局变化复用

位置：[滑动意图](../app/js/history.js#L403)、[惯性结束](../app/js/history.js#L1440)、[滚动判定](../app/js/history.js#L1466)。

触发：曾经朝底部滑动，后来停在历史内容；新内容或布局使滚动位置发生变化。旧意图在结束后仍存在，后续位置增加会更新其当前位置和最大位置，再进入“用户到底”判断。相反方向输入也没有完整清除旧意图。

最小修复：用户输入的方向与有效期必须有明确结束；布局变化不能续期或创造用户到底意图。只有本次真实手动到底、明确点击最新、发送等已约定入口才能进入跟随状态。不能重新引入阅读锚定。

影响：流式输出、工具展开、手动到底、最新／有新消息、发送跟随。按钮文字改变与新内容同一时间发生，不能据此把文字本身认定为唯一原因。

### B03 · 程序滚动的迟到事件被当成惯性

位置：[设置位置](../app/js/history.js#L465)、[接收滚动](../app/js/history.js#L1466)、[渲染推迟](../app/js/history.js#L653)。

触发：程序写 `scrollTop` 后，实际 `scroll` 事件晚于清理标记的一帧。事件随即被算成用户滚动，即使没有手指、指针或滚轮输入；新内容进入推迟渲染，结束后又补渲染、改位置，形成错误反馈。

最小修复：统一标注一次程序定位及其完成条件，用真实输入状态识别用户滚动；不靠一帧时间窗推断来源。不恢复持续保位补偿或旧锚点。

影响：首屏回底、最新／上下轮、发送后回底、历史插入一次性调整、惯性与流式渲染。

### B30 · 普通会话预览被误判为子 Agent

补查日期：2026-10-26。用户反馈 Codex 同项目会话切不过去，且同项目、跨项目切换都会显示提示。用户补充确认的完整原文为：**“正在查看子 Agent 的对话（只读）”**。此前讨论中的“正在浏览子代理”只是简称，后续定位、修复和验收按完整原文及实际状态核对。此分支没有在此前 29 项清单中具体识别，不能用“查过会话切换”代表已经覆盖。

位置：[缓存预览](../app/js/net.js#L83)、[预览调用](../app/js/net.js#L88)、[只读原生提取](../server/page/chat-extract.js#L720)、[队列栏展示](../app/js/history.js#L1044)。

触发：普通会话切换时已有缓存，`selectionPreview` 强制写入 `readonly: true`，表示缓存暂不可操作；`renderQueue` 却只凭 readonly 显示“正在查看子 Agent 的对话（只读）”及返回主对话按钮。原生输入框暂未挂载、登录等原因产生的只读也可能走同一展示。

隔离结果：普通缓存原值 readonly=false，预览后出现子 Agent 提示，未调用任何原生子 Agent 打开动作。已确认的是“只读状态被当成子 Agent 身份”，不是原生一定切进了子 Agent。

配对浏览器补验：在真实 v250 网页进行 Devin → Codex → Devin → Codex 的 Agent 缓存往返，监听队列栏实际渲染的子 Agent 返回控件。观察到普通预览阶段 readonly=true、子 Agent 列表为空时，仍渲染该提示／返回控件；实时内容恢复后 readonly=false，提示消失。没有点击查看子 Agent 或返回主对话。该结果确认了提示误判能在真实网页出现，但这次执行的是 Agent 切换，不能冒充同项目／跨项目的会话切换失败复现。

最小修复：缓存／加载／登录的不可操作状态与真实子 Agent 身份分开；只有确认实际子 Agent 时显示该提示及返回主对话。保留缓存只读，不能为消除提示直接允许操作旧缓存。

影响：普通会话切换的缓存预览、临时不可操作提示、真实子 Agent 返回入口。所属第 2 类，同时关联第 3、8 类。

**切换失败另行保留未确认状态。** 当前运行日志存在两条 `openAgent: 应用尚未打开所选项目，请检查电脑上的窗口`，但日志没有时间／目标标识，不能直接认定为本次用户操作。只读核对时，现有两个 Codex 窗口均有当前会话和可见输入框，未执行真实会话切换。额外隔离检查确认：原生导航已发起、1.8 秒内未读到新会话且回退入口不可用时，选择函数会先返回失败，原生稍后仍可能完成；此条件未在本次真实操作中确认。

后续核对重点是同项目切换的窗口可用判断、何时走新开项目窗口分支、实际路由与 thread 确认以及失败后的导航结束。不能把这部分失败直接归咎于缓存提示，也不能只改文案宣称切换已修复。

证据：`_shots/session-switch-audit-v250-20261026/proofs.mjs`、`proofs.json`（3 项隔离检查），`native-read.mjs`、`native-read.json`（此前只读原生状态）；该阶段没有点击或导航。新增真实界面证据见 `_shots/audit-reorganization-browser-v250-20261026/browser-results.json` 的 L11，实际进行了 Agent 缓存往返。两个阶段均未发消息或修改产品代码。

### B04 · Devin 已接受消息仍可能报发送失败

位置：[Devin 发送确认](../server/apps/devin.mjs#L260)。

触发：新增用户消息或队列已存在，但原生草稿短时间仍为原内容。当前循环先判断草稿不变并继续，跳过已经存在的接收证据；隔离检查分别覆盖已接受、已入队两种情况，均最终抛出未确认接收。

影响：Devin 普通发送、生成中排队、失败提示及草稿。不是把已经修复过的 Codex 旧判断再次算成当前缺陷。

### B05 · 接收待确认时提前消耗文档附件

影响：文档附件、待确认回执、重试和附件栏；图片上传与普通文本不需要整体改造。

### B10 · 自动 Retry 次数与实际点击不一致

## 6. 文件与媒体

### B22 · 多图编辑切换读取失败后锁在 loading

## 7. Fusion 与原生设置

### B18 · 手动决定后的失败没有终止阶段

位置：[fusionApply](../server/fusion/owner.mjs#L730)、[fusionDecide](../server/fusion/owner.mjs#L756)。

触发：在检查阶段点“小修”，进入 fix 后原生调用失败；或退回执行时失败。catch 只报状态，finally 清空 job，阶段仍是 fix／执行等活动阶段。隔离得到 phase=fix、job=null；后续新任务被阶段判断拒绝。

### B19 · Codex Fusion 回复依赖 DOM 是否挂载

### B20 · 同入口两标签页可以并发开始两份 Fusion

### B21 · 设置没有改变仍提示成功

### B31 · 配对已取消，命令仍等待浏览器退出或地址发布

补查日期：2026-10-26。用户明确在 Windows 上运行 `npm run pair`，偶发关闭网页及 Ctrl+C 后仍退不出。此前配对审查没有追完 CLI 信号、浏览器进程和地址发布的联合退出链路。

位置：[npm pair 入口](../package.json#L12)、[CLI 等待顺序](../cli/devices.mjs#L25)、[配对窗口 stop／exit](../lib/pairing-window.mjs#L25)、[发布子进程](../server/publish/pages.mjs#L11)、[审批页结束操作](../app/js/approval.js#L65)。

当前存在两条能够导致等待不结束的路径：

1. **Ctrl+C 只触发 stop，stop 不结束正在等待的 Promise。** `runPairingWindow` 接管首次 SIGINT；stop 先标记 stopped、清除有效期轮询、作废本次配对，再调用同步 `taskkill /PID /T /F`。该调用没有超时，也不检查返回状态。若调用失败且浏览器进程仍在，主函数继续等待 child 的 exit，轮询已经停止、后续 stop 也直接返回。隔离检查模拟 Windows taskkill 返回 1，确认配对已作废但函数仍未完成。这里不能宣称每一次 Ctrl+C 都无效：处理器是 once，第二次信号及 npm／cmd 进程组的真实行为尚未在 Windows 验证。
2. **窗口结束不能取消前面的地址发布等待。** CLI 启动窗口后，先 await `publishUrl`，最后才 await `windowDone`。发布使用的 gh 子进程没有结束预算或配对取消归属；即使窗口已正常退出，CLI 仍可能等发布结束。隔离检查先结束 windowDone、保持发布未完成，确认命令不结束；发布返回后又会打印“电脑配对窗口已启动”等已经过时的文案。该发布动作更新的是地址记录，不是同步整套 App 资源。

**关闭网页与浏览器进程退出还不是同一事件。** 审批页的“结束配对”按钮通过 API 作废配对；直接关窗口依赖独立浏览器进程退出，页面没有另一个关闭通知。当前代码在浏览器进程正常退出时可以正确结束，这一反例已经隔离验证。尚未确认用户现场究竟是浏览器仍驻留、taskkill 失败，还是发布子进程未结束，不能把其中一种猜测写成唯一原因。

简化方向：让本次 CLI 配对拥有一个明确的结束出口。Ctrl+C、真实关窗、主动结束和到期进入同一个结束过程；结束本次命令创建的发布与窗口资源，并明确处理 Windows 终止结果。不要让 CLI 退出无界等待地址发布或单一 child exit，也不要再叠加一套自动重试轮询。保留二维码、链接、手动码、电脑审批和固定地址发布语义。

影响：`npm run pair`、调用同一窗口函数的首次配对入口，以及 Windows 的独立审批浏览器。修复需区分 CLI 与 relay 内嵌调用，不能为了让 CLI 退出而终止中继、其他 Chrome／Edge 窗口、Agent 或已批准的设备授权。未修改产品代码、真实 pairing.json 或现有配对。

证据：`_shots/pair-exit-audit-v250-20261026/proofs.mjs`、`proofs.json`，执行当前源函数和 CLI 主体，依赖及等待时序隔离；包含正常退出反例。不是 Windows 真机或实际 GitHub 请求测试。

### B25 · HTTP 局域网入口与密钥认证条件不一致

位置：[CLI --lan](../cli/devices.mjs#L17)、[网页入口密钥](../app/js/auth.js#L4)。

最小修复：让局域网配对入口提供满足当前认证要求的访问方式，或明确将这个 CLI 模式标为不支持普通 HTTP 浏览器；不能通过取消入口签名或暴露私钥来解决。

影响：`npm run pair -- --lan` 的浏览器入口；现有 HTTPS 隧道、固定入口保持原规则。

## 10. 已核对但不计为确认漏洞的事项

1. **Cursor 发送缺少原生接收证明。** 当前适配器按键后返回，能证明确认标准偏乐观；本轮没有真实 Cursor 丢消息证据，不能直接算成已经发生的丢消息缺陷。若处理 B04，应一起明确三个适配器的返回合同，但不能借机扩大修改范围。
2. **等待次数不等于总等待预算。** 已有隔离结果为 10 次读取、每次 5 秒，合计 51.2 秒；初始 attach 的 30 秒总限已存在，不能仍称整个加载没有超时。其他原生操作遇到慢调用仍可能长等，需按实际入口统一预算；尚未定位一个新的确定加载死锁。
3. **发布按文件逐一更新，缺少整体事务。** 中途失败可能留下不完整资源；隧道与脚本也有多处生命周期管理。属于结构与故障风险，没有本轮“发布混版”的现场证据，不与缓存 B27 混算。
4. **Windows／macOS 自动关闭闲置窗口没有完整实现。** 非 Linux 的进程检查返回未知，真正原生关闭入口只实现 Linux／DISPLAY；相应窗口会保留。不能说已实现跨平台自动回收，也不能为追求回收率取消“不确定则保留”的判断。此为能力缺口，未算误关闭漏洞。
5. **跨手机同时编辑同一桌面输入框仍有竞争风险。** 普通操作的租约不是全局互斥发送锁，各连接的串行队列不能串行不同连接。本轮没有用真实双手机发送制造内容覆盖，列为待场景验证；已证实的共享 Fusion 并发单列 B20。
6. **语音模型首次加载、外部 Agent 排队、网络与系统权限。** 需要实际模型和设备证据。不能把模型自身慢、隧道外部不可达、系统权限不支持算成本软件已确认的逻辑漏洞。
7. **旧停用状态与重复保存。** 例如 `historyWaitingForIdle` 没有写入 true、旧质量分支不可达、Fusion 展示更新保存完整状态。这些可整理，但不是为了凑漏洞数的独立运行错误。
8. **通知断线补发并非完全缺失。** 已核对 SSE 开流有补发路径，不能仅因“投递层有去重”就断言离线通知一定丢失。B11 是轮次过滤位置错误，B12 是目标身份缺失，两者需要各自证据。

### 16.1 新增具体路径

#### B32 · Fusion 新建／打开会话的就绪互锁

- 位置：`app/js/net.js:112` 的 `applySelection`、thread 消息分支、chat 的 fresh 条件，以及 `app/js/history.js:75` 的 `queueChatRender`；上游为 `server/fusion/owner.mjs` 的 `fusionOpenHistory`。
- 触发：新建或打开 Fusion 只发布 thread 和 chat，没有接着发送 attached/projectReady。thread 变化清空 selectionReady 和 windowReady；chat 又要求 selectionReady 才能推进为 fresh，渲染队列要求 windowReady，因此互相等待。
- 证据：真实新建后没有正文且两个标志都为 false；重新 attach 后同一测试 run 完成方案、确认、执行、评审、done，文件内容正确。不是仅从变量命名猜测。
- 处理：统一“选择已确认”在 thread-only 切换中的完成出口，让匹配的首份正文有机会建立可渲染状态；保留 navigationId、sel 和旧回包过滤，不用“取消所有就绪判断”掩盖问题。
- 影响：Fusion 新建／历史和共享选择推进逻辑；普通 attach、项目打开、新空会话、旧消息迟到都要回归。不能从此证据推断用户每次 Codex 切换失败都是同一根因。

#### B33 · 未来消息时间被写入共享常用记录

- 位置：`server/agent/chat.mjs:239` 将 human.sentAt 传给 `lib/session-library.mjs:76` 的 `rememberSessionMessage`；`app/js/sheets.js:101` 的 `agentUsageInfo` 将负年龄钳为 0。
- 触发：原生记录因时钟差异或异常带有未来时间。直接写入只检查正数／有限／单调；一旦写入，正常较早消息不能回退。前端持续当成七天内。旧数据导入路径已经检查 `at <= Date.now()`，两条路径不一致。
- 证据：当前函数在内存库接受未来十天的直接时间；列表读取不消费 lastUsed 和拒绝未来 legacy 时间的反例检查均通过。这不是断言所有现有会话时间都错。
- 处理：明确原生真实消息时间的有效性语义，在统一写入点处理异常未来时间；存量异常按可验证的原生消息时间更正，不能改成按打开时间活跃。是否允许时钟容差需要确定语义后实施，不直接加并行回退规则。
- 影响：共享最近消息时间和常用筛选；星标、名称、原排序和消息正文不应改变。

#### B34 · fastRun 在异常处理范围外执行

- 位置：`server/ws.mjs:100–111` 的非 SWITCH_READS 快路由，`server/routes.mjs:102` 的 sessionLibrary，以及 `lib/session-library.mjs:51`。
- 触发：已认证消息提供非可迭代 entries；普通 JSON 解析成功，但 importLibrary 的 for…of 抛 TypeError。该 fastRun 不在普通 execute 的 try/catch，也不在读取快路由的 Promise.catch 内。
- 证据：本地随机端口真实 WebSocket、当前 attachWss 路由及当前 importLibrary，只有身份／文件系统用内存桩，捕获到未处理异常；生产 relay 没有收到畸形消息。其余 17 个协议子场景通过。未在生产试杀进程。
- 处理：收束快、普通两类路由的失败出口，并按该消息既有协议检查字段；不为此添加第二套通用兼容解码器。需要同时检查同步抛错和异步拒绝。
- 影响：WebSocket 分派和共享会话库导入；帧 ack、原有快读取取消、导航串行和客户端独立连接行为必须保持。

#### B35 · Cursor 后台窗口快捷新终端无结果确认

- 位置：`server/apps/cursor.mjs:164` 的 newTerminal 仅发 Ctrl+Shift+Backquote，`server/agent/terminal.mjs:88` 在 Cursor 分支没有检查终端是否创建，就发“已新建终端”。

### Q01 · Retry 要人为往下滑动才出现：现场现象已记录，根因待定位

- 用户现象：手机已经可以显示 Retry，但上游出现后不会自行展示，需要下滑才出现。
- 归类：04 原生交互，关联 02 滚动与延迟绘制；新增 CAP06。此项不直接增加 B 编号，避免将未经证实的原因计为漏洞。
- 已读链路：`server/agent/updates.mjs` 的容量变动观察 → `server/agent/chat.mjs` 的读取／发布 → `app/js/net.js` chat 接收 → `queueChatRender` → `renderChat`。`app/js/history.js:653` 在触摸、惯性、滚动或滑块拖动时会延迟整个列表绘制；`flushSettledChat` 负责收尾。B37 的误识别也可能改变容量项内容，但没有证据证明这就是本次延迟原因。
- 必须区分三种现场状态：①收到的 chat 还没有 capacity/Retry；②数据已收到但 DOM 尚未更新；③DOM 已有按钮，只是位于当前可视区下方。不能只凭“滑一下就出现”判断服务器没同步。
- 后续具体检查：分别记录首次原生 banner/Retry 可用、手机匹配 sel 回包、notice DOM 生成、按钮相对视口位置及当时跟随／手势状态；覆盖静止已到底、自由阅读、惯性刚结束、原生倒计时结束四种时序。不得记录实际会话正文或按钮外的私密内容。
- 处理原则／影响：只修已确认的通知读取、绘制或布局结束出口；已跟随时保持最新提示可见，自由阅读时不强制回底，不新增阅读锚点。涉及容量提示与聊天显示，不更改真实 Retry 动作或自动次数策略。当前尚未定位，未写成已修复。

### B36 · 容量提示重复 Retry，按钮被放到下一行

- 位置：`server/page/chat-extract.js:654–666` 选取包含按钮的横幅容器后，直接取 `banner.innerText` 作为正文，又把同一个 Retry 放进 `b`。`app/js/chat.js:228–234` 先写正文，再追加 `.btns`；`app/app.css:592–598` 使用独立 flex 块和上边距。
- 证据：当前检测函数输入真实形式的横幅后，得到正文末尾 Retry，同时 b=[Retry]；源码和用户截图对应。带按钮仍整体取 innerText，是重复文字的来源，不能用全局删去字符串 Retry 来修。
- 具体方案：提示正文和原生动作分别提取，仅排除对应按钮节点的可见文字，保留真正的错误解释和倒计时；容量卡单独使用“提示正文＋右侧按钮”的同行布局。窄屏允许提示内部换行，按钮保持独立点击目标。仍只有一个真实绑定的 Retry，不伪造按钮，不删除其他消息的 retry 文案。

### B37 · 工具摘要里的关键词被当成容量横幅

- 位置：`server/page/chat-extract.js:641–668` 的 `codexCapacityItem`；`app/js/chat.js:228` notice 渲染；`app/app.css:592` 的居中圆角提示样式。

- 证据：执行当前函数确认该工具文本会被误报；pre/code 的同样文字会正确排除，说明是摘要容器覆盖缺口，不能泛称所有引用都未过滤。截图中的完整命令包含上一轮测试脚本正文，而对应脚本自身确有 capacity 检查语句；这与误判路径一致。未在原生页面抓到该行身份，因此不把截图节点对应关系说成已实机确定。

### B38 · 有草稿且未编辑时，首击按钮先改变布局／被拦截

用户的“为编辑状态”按上下文理解为“非编辑、未聚焦的空闲收起状态”；本项检查的是**有内容的草稿**，不是原先明确的空输入框 compact 首击展开行为。

- 位置：`app/js/composer.js:503–508` 的 document capture pointerdown；`composeIdleWanted`、`setComposerPresentation:437`；`.composerBox` capture click 的 `494–497`；`app/app.css:793` 非空空闲草稿限高。
- 两条具体路径：①按下内部按钮时先将 composerEngaged=true，立即取消 idle 并 autosize，footer 在 click 之前已经增高，原坐标可能不再落在原按钮；②从 compact 退出后 400ms 内的按钮点击会被统一 preventDefault/stopPropagation，不区分同一手势的残留事件和用户新点的一次按钮。计时只在 oldCompact=true 时设置；有内容的普通 idle→展开不会另设这个计时，不能把两条路径混称为同一原因。
- 证据：当前事件函数隔离执行确认非空草稿在 pointerdown 阶段先展开；当前 capture click 在模拟刚退出 compact 的时间窗内拦截真实按钮，超过 400ms 又不拦截。高度只用几何桩证明时序，未声称测到实体手机移动多少像素；各个按钮的实际命中仍需要坐标回归。
- 具体方案：点击可见按钮应直接执行该按钮动作；有草稿时不能为了“唤醒编辑”先消费该次按钮操作。输入框展开时机与动作点击分开，避免 pointerdown 到 pointerup 之间重排目标；去除不区分来源的 400ms 全局禁点，若确有同一手势残留只处理该手势，不屏蔽独立新点击。不删除空闲节省空间、编辑按字数展开或草稿同步功能。
- 影响：输入框内外的模型、项目、文件、附件、输入历史、换行和发送／追加的点击时序；具体受影响按钮不能仅凭同在 footer 就全称失效，需逐项回归。必须保留草稿／光标，且展开不能重新触发自由阅读回底。新增 MSG13，主要归 01，关联 04／09。
- 与上轮结果的关系：原先模型坐标重开失败、DOM 控件触发成功没有确定根因；B38 现在提供了应专项验证的实际事件链，不能再用“DOM 触发通过”替代真实首击命中，也不能在无当时状态记录时将所有旧失败倒改为已复现 B38。
