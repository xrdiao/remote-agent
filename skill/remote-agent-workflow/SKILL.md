# Remote Agent 排查、修改与验证流程

本流程总结本项目历史会话中的实际要求与验证方法。开始工作时先读取当前 [AGENTS.md](../../AGENTS.md)，结合用户本次要求和已经确认的范围执行；历史记录中的发布、重启或测试授权不能直接扩大当前任务。

## 1. 先明确范围与现场

- 默认使用简体中文；必要时给出中文与英文术语，避免堆砌。
- 区分用户要求的是排查、方案、文档、代码实施还是发布。请求编写方案不等于授权修改产品代码。
- 修改代码前，列明文件、每处改法、影响范围和验证方法，取得用户确认；确认范围内连续实施，不为常规步骤反复询问。发现必须增加的文件或范围外问题，说明实际缺口后确认新增范围。
- 允许在已确认范围内重构；不顺手优化，不改无关 Agent 或公共逻辑，不动 `scripts/page-exports.json`。用户未要求时，不添加额外保护、兜底、兼容分支或自动重试。
- 查看 `git status` 和已有差异，保留用户及其他工作留下的暂存、未暂存和未跟踪文件。不能用检出、重置或整段回退覆盖它们。
- 记录与本问题有关的软件版本、网页资源版本、relay 实际加载版本、模式、项目、host、窗口和会话身份。源码已改、网页已发布和进程已加载是三件事。

## 2. 建立本次基准

Ubuntu 回归以**修改前的当前工作区内容**为基准，包含已有本地改动，不沿用历史版本号或直接拿 Git HEAD 代替。

1. 只为受影响文件、行为和必要现场建立基准；需要保存快照、截图或日志时放在 `_shots/<本次任务>/`。
2. 用户要求对照 GitHub 时，读取实际远端提交，例如 `git ls-remote origin refs/heads/master`；本地 `origin/master` 只代表上次获取的结果。网络不可用时写明未核对。
3. 对照远端确认本地已有差异的归属；实现与回归仍依据本次工作区基准，不能把既有修改算成本轮成果。
4. 修改协议或 page helpers 前先跑 `npm run check`。不要为文档任务启动真实 Agent、改模型、重启 relay 或发布网页。

## 3. 按事实找根因

沿“用户操作 → 手机请求 → relay 路由与连接 → 原生接受／执行 → 数据读取 → 手机显示”的实际链路排查；从功能逻辑、数据归属、请求时序和状态变化解释现象。

| 检查维度 | 要核对的事实 |
|---|---|
| 身份与归属 | 哪台电脑、哪个软件、host、真实项目目录、CDP target、原生会话、请求和轮次；标题相同不表示目标相同 |
| 状态与生命周期 | 谁创建和持有状态，何时绑定、重置、释放；手机断线与原生停止是否被混为一谈 |
| 时序 | 操作前状态、提交、原生接受、生成结束和迟到回执；旧回调是否影响新请求或新会话 |
| 数据来源 | 原生记录、页面当前可见内容、缓存和历史的区别；实际能力与静态配置的区别 |
| 操作语义 | 普通发送、排队 Queue、立即追加 Steer、停止、归档、删除和清空各自的接受依据 |

排查时遵循以下判定：

- 结构重复、分支数量或多套机制共存，不足以证明存在故障；先核对职责和可达调用路径。
- 区分已经复现的故障、条件成立的风险、维护成本、待验证猜测和测试脚本失败。没有同场景基准对照，不把新发现直接称为本次回归。
- 点击成功、请求返回、输入框清空或手机出现气泡，不等于原生已经接受；原生回复结束，也不等于任务已经验收完成。
- 只读、最小复现优先。疑似原生问题时，用同软件、同模型、同强度的桌面路径对照；原生也失败只能证明该路径同样有问题，不能据错误文字推断账号、限速或上游内部根因。
- 沙箱 `EPERM`、浏览器本地网络权限、测试夹具或依赖装载问题单独处理，不为它们改产品逻辑。
- 不用增加条件、隐藏入口、吞事件、延长等待、强清草稿或重复发送压住症状。结果未知先核对，不自动重做可能已经执行的写操作。

## 4. 提交可执行的修改方案

方案至少包含：问题及证据、根因或仍未知之处、允许修改的文件、每处改法、直接影响范围和可核对的完成标准。

按实际依赖分批，复用已经存在的读取、回执、连接、会话管理和窗口租约。说明哪些能力属于共享模块、哪些只是某个 Agent 的专用分支，避免把局部修复扩成全仓重构。

用户确认后只实施该方案。授权和已确认偏好在当前任务中持续有效；只有范围扩展、真实阻塞或必要外部权限需要再次确认。确认问题应指出对应规则及具体缺口，不能只说“需要权限”。

## 5. 以最小改动实施

- 从状态的实际拥有者修复问题，复用已有同类能力，不复制近似实现来完成任务。
- 保持受影响功能原有语义和效率；不靠重复读取、嵌套等待或新的循环维持表面正常。
- 保留真实未发草稿、既有改动、收藏和无关任务。只处理本任务有明确归属的请求、会话和窗口。
- 前端有改动时同步实际修改资源的引用版本、`APP_VERSION` 和 Service Worker 缓存；版本更新与发布授权分开处理。
- 分批完成后在任务记录中标明已处理项和证据。相关修复全部完成后统一进行配对浏览器检查，避免每个小项重复消耗原生额度。

## 6. 分层验证，检查到位即可

| 层次 | 用途 | 结果边界 |
|---|---|---|
| 静态与受控检查 | 语法、协议、page 导出、实际函数、状态机、竞态和错误路径 | 测试替身、受控时钟和合成会话不能算真实原生执行 |
| 既有配对浏览器与原生对照 | 验证本次请求、原生会话、模型、回执和显示的真实闭环 | 桌面 Chrome、模拟尺寸和合成后台事件不能代表 iPhone／Safari 真机 |
| 用户手机验收 | 用户使用既有入口复现原场景并检查受影响功能 | 未执行、受阻或无证据的项目保持待验 |

只检查修改及实际受影响的功能。新增测试验证可观察行为和必要的不变量，不机械匹配实现文字；低影响可逆改动不额外堆测试。已通过且未受后续修改影响的场景不重复执行。

修改完成后必须运行 `npm run check`，并检查本次差异和空白错误。该命令结果以当次输出为准，不把历史测试数量写成本轮结果。沙箱导致检查无法执行时，定位限制并使用可获授权的运行方式；不能删检查、改快照或把未执行记为通过。

## 7. 配对浏览器检查方法

用户在 2026-11-02 明确要求恢复自动验收，并持续授权“配对浏览器打不开时自动恢复”。后续每轮受影响功能检查前执行 `node scripts/paired-browser.mjs`，无需再次请求相同的恢复许可；产品代码修改仍须先确认方案。

1. 复用用户既有配对浏览器和身份，不重建配对，不输出密钥、令牌或无关会话内容。不要复制整个浏览器资料目录来获得测试身份。本机配置登记在 gitignore 的 `_shots/paired-browser.json`：`appUrl`、`browser.executable/profile/port`、`relay.dataDir/args/env`，只保存原资料目录、端口和隔离服务启动配置，不保存凭据。
2. 恢复脚本检查登记的原资料与服务数据、端口和原配对认证。已运行时直接复用；服务或浏览器未运行时，只启动登记的隔离验收 relay 和原浏览器资料目录，再检查认证。不要重启正式 relay；原资料缺失或认证失败时记录实际阻塞，不创建新身份。恢复结果与日志位于 `_shots/paired-browser/`。
3. 记录原配对页选择、草稿、视口及相关缓存，并记录本次受影响的普通原生窗口的 target、会话、模型、草稿和运行状态。恢复环境本身不发送模型消息、不新建 Fusion run；原配对页已运行时保持该页状态。
4. 需要验证未加载的代码时，使用临时标签、当前本地资源和隔离 relay。隔离测试自己的存储和元数据，复用真实认证链路；不通过修改原页面业务状态伪造通过，不把拦截静态资源说成网页已发布。
5. 真实操作只在已授权的测试项目和目标中进行；不刷新或停止用户正在工作的原生页面。测试模型和消息数量遵循本任务授权，不能为收集答案批量调用。
6. 对本次受影响链路统一检查；明确每个请求是否只提交一次、是否由正确原生身份接受、结果是否回到正确入口。
7. 浏览器临时权限只按实际授权调整，检查后恢复；权限被拒时如实说明，不以新配对绕过。
8. 归档本次可归档的测试会话，释放本轮临时租约、连接、窗口、进程和标签，核对普通现场。保留登记的配对验收浏览器、原资料和隔离 relay，避免下轮再次因清理而不可用；只清理本轮一次性资源。发现无法解释的状态差异时记录事实，不能擅自覆盖原存储后宣称完全恢复。

Fusion 测试采用同软件串行、每软件一个测试窗口；零子任务、多子任务、补做、依赖、停止和恢复可先用受控状态机验证，再做必要的真实闭环。具体范围见 [Fusion 方案](../../docs/fusion-multi-agent-plan-20261101.md)。

## 8. 交付与续做记录

交付说明应回答：改了什么、为什么这样改、实际通过哪些检查、哪些仍受阻或待验，以及代码是否已被运行环境加载。

- 对照本次工作区基准检查改动和受影响行为；不能声称未执行的平台或原生路径通过。
- 区分“实现完成”“标准检查通过”“浏览器验证通过”“手机验收通过”。新增诊断记录只提供证据，不等于修好业务问题。
- 需要更新网页或重启 relay 才生效时明确说明；未获授权不自行发布、重启正式服务、提交或推送。已有明确授权时按授权执行，无需再次索要同一许可。
- 提交、tag 和 PR 不加入 AI 工具署名；未获明确要求不执行 Git 提交或推送。
- 在任务文档中保留范围、基准、实际结果、证据路径和待办，后续从该状态继续，不重做已经通过且未受影响的工作。

大改后的手机验收按实际影响选取：连接并 attach、发送及滚动、历史切换、模型／强度、文件引用高亮、终端输出与命令；Fusion 按新版主 Agent 与任务编排完成完整流程。当前功能基准见 [基准索引](../../docs/baselines/README.md)。
